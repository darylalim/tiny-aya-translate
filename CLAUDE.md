## Project

Streamlit application for translation using Cohere Labs Tiny Aya Global on Apple Silicon with MLX. The app translates text across 67 languages with local inference via the `mlx-community/tiny-aya-global-8bit-mlx` model. It is a single page: one language row, two side-by-side panels, two buttons. A Document tab — file uploads parsed with LiteParse, OCR for images, a token-aware chunker, `st.tabs` around both flows — existed until 2026-09-13 and was removed end to end (last commit carrying it: `075ad4c`); nothing below describes it.

## Stack

- Python 3.13+ with uv for project management
- Streamlit for UI
- watchdog for Streamlit's file watcher, listed in `dependencies` **explicitly** because Streamlit's own requirement on it is gated `sys_platform != 'darwin'`. On macOS Streamlit therefore ships *without* it and falls back to `PollingPathWatcher`, which is what prints "For better performance, install the Watchdog module" on every launch. Streamlit's accompanying `xcode-select --install` hint is stale — the macOS wheel (`cp313-cp313-macosx_11_0_arm64`) is a compiled FSEvents binding but is **prebuilt** on PyPI, so nothing is built locally. It belongs in `dependencies` rather than the `dev` group because the server process imports it, not the tests. Confirm it took with `uv run python -c "from streamlit.watcher import path_watcher; print(path_watcher.get_default_path_watcher_class().__name__)"` → `EventBasedPathWatcher`
- mlx-lm for translation inference on Apple Silicon. Those three are the whole `dependencies` list: `liteparse` (the document parser) was removed with the Document tab on 2026-09-13 via `uv remove liteparse`, which rewrote `pyproject.toml` and `uv.lock` together

## Structure

- `streamlit_app.py` — main app: config, pure functions, Streamlit UI
- `test_streamlit_app.py` — pytest unit tests for pure functions
- `test_streamlit_ui.py` — pytest UI tests for Streamlit interface
- `.streamlit/config.toml` — the project's own theme ("Reading Room"), dark-first, both modes stated in full; the comment block at the top of the file is the full record of every value and measured ratio, so cite it rather than duplicate it; see Model and theme. Also carries `[browser] gatherUsageStats = false`; see Page chrome
- `assets/favicon.svg` — the local favicon (the Material `translate` glyph in the accent), inlined as a `data:` URL by `set_page_config`; a test asserts it resolves. See Page chrome
- `.github/workflows/` — `ci.yml` (checks + auto-publish release) and `release.yml` (manual bump), sharing `.github/scripts/release-notes.sh`; see Automation and Releases
- `.claude/settings.json` — ruff/actionlint/ty/pytest hooks and the protected-path guard; see Automation
- `assets/screenshot.png` — README hero image; see Screenshots

## Commands

```bash
uv sync                                                      # install dependencies
uv run streamlit run streamlit_app.py                        # run the app
uv run pytest -v                                             # run tests
uv run pytest -k stream_translate -q                         # one topic
uv run pytest test_streamlit_app.py::test_buttons_use_width_stretch  # one test
uv run ruff check --fix .                                    # lint
uv run ruff format .                                         # format
uv run ty check                                              # type check
```

When working with Python, invoke the relevant `/astral:<skill>` for uv, ty, and ruff to ensure best practices are followed.

- Bare `python` is **not** on `PATH` (`command not found: python`); everything goes through `uv run`, one-off scripts included (`uv run python <script>`)
- `uv run streamlit docs st.<command>` prints the exact signature and docstring from the *installed* Streamlit — use it instead of recalling an API from memory. The `developing-with-streamlit` skill routes to version-matched reference docs bundled inside the venv at `.venv/lib/python3.13/site-packages/streamlit/.agents/skills/`, not to anything in this repo; that tree also carries ready-made theme configs under `assets/templates/themes/configs/` (12 presets, `nord.toml` among them)
- A throwaway `uv run python -c` that **imports** `test_streamlit_app` or `streamlit_app` buries its output under dozens of `missing ScriptRunContext!` warnings, because importing the app runs Streamlit calls outside a script run. For a quick calculation, inline the few lines you need rather than importing the module

## Automation

- CI (`.github/workflows/ci.yml`) has **two jobs**. `check` runs on `macos-latest` (Apple Silicon, so `mlx-lm` installs natively) for pushes to `main` and PRs: `uv sync --locked`, `ruff format --check .`, `ruff check .`, `ty check`, then `pytest -q`. Note `--check` — unformatted code fails CI rather than being auto-fixed. `release` is the auto-publish job described under Releases
- The test step is **bare `pytest`**, not the hand-listed pair it used to be. `pyproject.toml` sets `testpaths = ["."]`, so collection follows the repo — naming the two files meant a third test module could be added to a green CI that never ran it, and the same list was duplicated in the `Stop` hook, `release.yml`, the README, and this file. Confirmed identical coverage: 94 tests collected either way, 51 in `test_streamlit_app.py` and 43 in `test_streamlit_ui.py` (re-checked 2026-09-13: the docked controls added three — the fold budget, the `wrap=False` AST pin and the AppTest docking pin — taking 91 to 94; earlier that day the Document tab's removal took the suite from 166 to 83, the rerun-precondition guard made it 84, and the swap-guard, swap-clip, settled-name and `clip_to_input_cap` tests 91, all the same day; the hub-defaults test had made it 166 on 2026-09-12, the spinner-slot guard test 165 earlier that day, the theme pass had taken it from 158 to 163 and the page-load fix to 164)
- Both jobs carry **`timeout-minutes`** (30 on the macOS `check`, 10 on the ubuntu `release`; `release.yml` also 30). GitHub's default is **6 hours**, and macOS bills at 10x — so an unguarded wedged run costs ~3,600 billed minutes. This is the same cost concern that put the `release` job on ubuntu, applied at the point of largest exposure
- `.python-version` is **tracked, deliberately** — it is the only thing pinning CI's interpreter. It was previously gitignored alongside `.env`/`.venv/`, so a fresh clone (which is every CI run) left uv with nothing but `requires-python = ">=3.13"` and it resolved the newest match; CI would have silently moved to 3.14 on release day. It also makes README's "uv installs a matching interpreter from `.python-version`" true, which it was not while the file was untracked
- Actions are pinned to `actions/checkout@v7` and **`astral-sh/setup-uv@v9.0.0`** — note the exact patch version on the second one, and **do not shorten it to `@v9`**. setup-uv stopped publishing floating major and minor tags after `v7.6`: its v8.0.0 release removed the workflow that maintained them, so the tag list runs `v7.6.0`, `v7.6`, … `v8.0.0`, `v8.1.0`, … `v9.0.0` with **no bare `v8` or `v9` ref at all**. `@v9` fails the run in ~6 s with `Unable to resolve action ... unable to find version`, *before any job starts* — which also means `release` is skipped by `needs: check` and nothing is tagged. This was shipped and failed once; the release-note line that caused it ("Remove update-major-minor-tags workflow") reads like internal housekeeping and is not. `actions/checkout` **does** still publish major tags, so `@v7` there is correct. Verify a pin with `gh api repos/<owner>/<repo>/git/ref/tags/<tag>` rather than reading a version off `releases/latest`, which reports `v9.0.0` whether or not `v9` exists
- Checked before bumping from v4/v5 in August 2026: checkout v5-v7 are node24, a credentials-file change, and a fork-PR block that only affects `pull_request_target`/`workflow_run` (neither used here); setup-uv v7-v8 are node24 plus internal removals. **setup-uv v9 deliberately increases Actions cache usage** — flagged as breaking by upstream for that reason, so watch cache storage if it ever matters
- The sync is `uv sync --locked`, not a bare `uv sync`. `uv.lock` records the project's own version, so a hand bump that edits `pyproject.toml` alone leaves the lock stale — and a bare `uv sync` **rewrites it in place and goes green**, which would let the `release` job tag a commit whose lock disagrees with its pyproject. `--locked` fails the run instead. The same swap was made in `release.yml`, which claims "same gate as ci.yml" and now actually is
- `concurrency` is declared **per job**, not at workflow level. A workflow-level `cancel-in-progress: true` cancels the *whole run*, so a second push landing during a release could kill the job between `git push --tags` and `gh release create`, leaving a pushed tag with no release. `check` keeps `ci-${{ github.ref }}` / cancel-in-progress; `release` takes `group: release` / **no** cancel, the same group `release.yml` uses, so the two release paths serialize against each other repo-wide
- `.claude/settings.json` carries **four** hooks, and three of them encode a trap worth knowing:
  - `PostToolUse` → **ruff** on `*.py` edits only (whole project, so edited files may be reformatted underneath you). The two commands are deliberately **not** chained with `&&`: `ruff check --fix` exits 1 whenever unfixable violations remain, which skipped `ruff format` on precisely the files that needed it — verified by reproduction, an unformatted `x    =   undefined_name` survived the chain untouched. It runs `check --fix .; rc=$?; format .; exit $rc`, so formatting always happens and the lint status still propagates
  - `PostToolUse` → **actionlint** on `.github/workflows/*.y{,a}ml` edits, `exit 2` on findings. It redirects **stdout to stderr** (`actionlint "$f" >&2`) because actionlint reports on stdout (measured: 583 bytes stdout, 0 stderr) while Claude Code surfaces only *stderr* on `exit 2` — without the redirect a broken workflow fired the hook correctly and reported nothing
  - `Stop` → `ty check` + `pytest`, unconditional. It runs on docs-only sessions too; that is the accepted price of not letting a heuristic skip the run that mattered — and the price is small enough to be worth stating rather than re-guessing: 4.19 s for the 94 tests, 1.37 s for `ty check` (both re-measured 2026-09-13 after the docked controls; 4.16 s for 91 and 1.3 s after the swap fixes earlier that day — 3.89 s for 84 after the rerun-precondition guard and 3.54 s for 83 after the Document tab's removal, earlier that day; `uv run pytest -q` and `/usr/bin/time -p uv run ty check`, ty 0.0.80 — the 83 removed document tests were the other half of the old figure; 6.91 s for 166 on 2026-09-12 after the hub-defaults test; 7.19 s for 165 earlier that day after the spinner-slot guard test; ty 0.0.80 on 2026-09-11, when 163 tests ran in 6.88 s and 158 in 6.5 s)
  - `PreToolUse` → the fail-closed guard. Blocks edits to `uv.lock` and `.streamlit/secrets.toml`, and blocks hand-editing `version` in `pyproject.toml` (use `uv version --bump`, which rewrites the lock as well). It reads stdin **once** into a variable — `jq` consumes stdin, so the second query for `.tool_input.new_string` would otherwise return empty and the guard would silently pass everything. Its version regex is anchored (`^[[:space:]]*version[[:space:]]*=`) so `target-version = "py313"` under `[tool.ruff]` stays editable; without the anchor no ruff config change would be possible

## Releases

- Versioned with SemVer in `pyproject.toml` (`version`); currently pre-1.0 (0.x). First tagged release was `v0.8.2`. Tags carry a `v` prefix; `pyproject` stays bare
- There are **two** ways to cut a release, and both **publish immediately**. There is no draft and no review step: the release goes live, watchers are notified, and the README's release badge moves the moment the job finishes. Deleting a release afterwards does not unsend the notification, so the review that used to happen on the draft has to happen *before* the push — in the commit subjects, which are now the notes:
  - **`Release` workflow** (`.github/workflows/release.yml`), run from the Actions tab with a `patch`/`minor`/`major` choice. It runs the full CI gate, bumps the version, generates notes, commits, tags, pushes, and publishes. This is the path that *performs* the bump, and `uv version --bump` is the reason to prefer it
  - **CI's `release` job** (`.github/workflows/ci.yml`), which publishes a release for any version bump that lands on `main` by hand. Bump `pyproject.toml` + `uv.lock`, commit, push — the tag and the published release follow automatically
- Both publish steps pass **`--verify-tag`**, which is not redundant with the tag push in the step above it. `gh release create` *creates* a missing tag itself, resolving it against the default branch's HEAD — so a tag push that failed silently would produce a live release attached to the wrong commit. With the flag the step aborts instead, leaving the tag and release consistent. `--latest` is deliberately unset, which is **not** the same as passing it: unset means GitHub picks the Latest release automatically from date and version, which is right while the newest release is always the highest version. Each step captures `gh`'s stdout (the release URL) into `$GITHUB_STEP_SUMMARY`, because with nothing to review in the Releases tab the run summary is where the link is wanted
- The two cannot double-release, for **two independent reasons**, and the first is the same GITHUB_TOKEN rule that shapes `release.yml`: the bump commit it pushes is authenticated with `GITHUB_TOKEN`, so it does not start a CI run *at all*. Even if it did, CI's gate skips any version that is already tagged — which `release.yml` has done by then. They also share the `release` concurrency group, so they cannot interleave
- CI's gate is **"pyproject declares a version with no tag"**, deliberately not a diff against the parent commit. A push can carry many commits, a re-run would fire twice, and a force-push has no useful parent; the tag check is idempotent and answers the same question. It reads the remote (`git ls-remote --exit-code --tags origin`), which is the real source of truth for "has this shipped"
- CI's `release` job runs on **`ubuntu-latest`**, not the `macos-latest` the checks need — it is plain `git` + `gh`, and macOS runners bill at 10x. It reads the version with the runner's preinstalled `python3` + stdlib `tomllib` rather than `uv version`, the project's usual route: `uv` performs interpreter discovery and would download a whole Python to read one TOML field, on **every** push to `main` including the ones with nothing to release
- Its `permissions: contents: write` is declared **at the job**, overriding the workflow-level `contents: read`. The `check` job stays read-only
- There is no artifact to publish: `pyproject.toml` has no `[build-system]` and `uv.lock` records the project as `source = { virtual = "." }`. A "release" here is only a tag plus a GitHub Release
- The workflow bumps with `uv version --bump <part>`, which rewrites `pyproject.toml` **and** re-locks `uv.lock` in one command — a version bump touches **two** files, because the lock records the project's own version. Bumping by hand and forgetting the lock leaves it to be rewritten by the next `uv` command, potentially after tagging
- Release notes are generated from **conventional commits** since the previous tag, grouped into Breaking changes / Features / Fixes / Performance / Refactoring / Documentation (`chore`/`test`/`ci`/`build` are omitted as noise; the compare link covers them). **Breaking changes** is any type with a `!` before the colon — including the four otherwise-omitted types, so `build!:` or `chore!:` still ships as a breaking change — listed first and *only* there: `section`'s pattern has no `!`, so nothing is filed twice, **provided the scope is `[^)]+`**. It was `.+`, and POSIX ERE is leftmost-longest, so the scope group swallowed a `!` and everything up to a later `): ` in the subject — `feat(ui)!: drop X (and Y): text only` was filed under Breaking changes *and* under Features as `- text only`, and a plain `feat(ui): foo (bar): baz` rendered as `- baz` (reproduced through the script under bash 3.2; an unscoped `feat!:` was never affected). The section was added on 2026-09-13 because before it a `feat!:` subject matched nothing and silently vanished from the notes: the Document tab's removal would have shipped under Features beside three Fixes for the tab it removed. Only the subject form is read; a `BREAKING CHANGE:` footer is in the body, which the script never sees. On 0.x a removal is a **minor** bump, not a patch, and nothing enforces that — look for a `!` in the range before choosing `patch`. GitHub's own `--generate-notes` is useless here — it aggregates merged PRs, and commits land directly on `main`. That output now ships **unreviewed**, so a commit subject is user-facing copy the moment it is pushed. The hand-written Highlights/Requirements/Run blurb that the draft existed for is gone; if it is ever wanted back it belongs in `release-notes.sh` as a static footer shared by both paths, **not** as a restored draft on one of them
- That generator lives in **`.github/scripts/release-notes.sh`**, called by both workflows so they cannot drift into describing the same commits differently. It takes the output path as `$1` and `VERSION`/`REPO_URL` from the environment, and must run **before** the new tag exists or `git describe --tags --abbrev=0` returns the tag being created and the range collapses to nothing. It runs on **both** runner OSes, and macOS ships **bash 3.2**, so no bash-4 syntax: no arrays, no `${x,,}`. That is why the empty-range (first-release) case is spelled as two separate `git log` calls instead of an interpolated `$range` — the empty form needs an unquoted expansion, and bash 3.2 has no safe empty array. `set -o pipefail` is on, so each `section`, and `breaking`, needs its `|| true`: `grep` exits 1 for a commit type absent from the range, which would otherwise fail the run
- The workflow is `workflow_dispatch`, **not** tag-triggered, and that is deliberate: a tag pushed with `GITHUB_TOKEN` does not trigger other workflows, so an `on: push: tags:` release job would silently never fire
- Every `${{ }}` value is passed through a step-level `env:` block rather than inlined into a `run:` script — the standard defense against workflow command injection. `github.ref_name` is a branch name and must never be inlined
- `main` has no branch protection or rulesets, which is what lets the workflow push the bump commit directly. Adding protection means allowlisting the Actions actor
- Hand-bumping is now a **supported path rather than a fallback**: `uv version --bump <part>` → commit `pyproject.toml` + `uv.lock` **together** → push to `main`, and CI tags and publishes the rest. Do not tag by hand as well; the gate would then see the tag and skip, leaving no release. If CI is bypassed entirely, the fully manual sequence is still bump → commit both files → `git tag -a vX.Y.Z` → `git push origin vX.Y.Z`, and tags must be pushed explicitly — a branch push (including via GitHub Desktop) does not carry them, verify with `git ls-remote --tags origin`
- Committing the two files **separately** is the one way to get a wrong result: pushing a `pyproject.toml` bump without its `uv.lock` fails `uv sync --locked` in `check`, and `release` never runs (`needs: check`) — which is the intended outcome, but the release simply does not appear rather than announcing why. The failing step names it

Note that `--server.headless true` is the one flag that makes the *server* reach out: `bootstrap.py` calls `net_util.get_external_ip()` (a GET to `checkip.amazonaws.com`) to print the "External URL" line, only in headless mode — the documented run command does not pass it, so a user's launch makes no such request
- The shot needs a **real translation**, not an empty app — but the old reason for saying so is gone. It used to be that the output `text_area` was `disabled=True`, so genuine output rendered in the same muted grey as placeholder text; settled output now goes through `render_output`/`st.code` and reads at full contrast, and the empty-state placeholder is `Translation appears here`. It matters more now than it did: the hovered fill sinks toward the dark page rather than lighting, so a hovered Translate reads *pressed-in*, and a baked-in hover state reads as a deliberate colour choice, not a mistake. Verify with `getComputedStyle(btn).backgroundColor`, not by eye. The **cursor itself is rendered into captures** — a first attempt on 2026-09-11 had it sitting over the output panel — so park it at the far bottom-right of the viewport, outside the region being captured, not merely off the button: the `computer` tool's `hover` action does it (`(1076, 836)` is outside the `[51..1029, 58..811]` frame). - macOS `screencapture` **does not work from this environment** — `could not create image from rect` for every region *and* every `-D` display, because the process has no Screen Recording permission and only the user can grant it. Do not burn time debugging the rect; use the Chrome extension
- The Chrome `computer` **`screenshot`** action downsamples (a 1080px-wide viewport returned 883px for the 2026-08 capture and 875px on 2026-09-11 — the factor is not fixed, so read it off the returned frame each time; it was 1.234 on 2026-09-12 and 1.205 on 2026-09-13, when 1080 came back as 896 — and **1.0** later that same day, when a 1080×783 viewport came back as 1080×783, and 1.0 again for the docked-controls capture at 1080×839, while a 1920-wide viewport the same afternoon came back as 1568, factor 1.2245 — so do not assume it is ever above 1, or ever 1), while the **`zoom`** action re-renders its region at *native* resolution. `zoom` takes `save_to_disk`, which writes a PNG under `/var/folders/…/claude-chrome-screenshots-*/` — that file is the hero's source, opened with PIL for the pixel gate below. Out-of-range values fail with a message that misleadingly quotes the viewport size, which sends you looking in the wrong place

Source-level tests guard against re-inlining any `height=<digit>` (a regex since the retune — the old `height=450` pin would have waved a re-inlined 438 through) or duplicating either warning literal. The input `text_area` keeps its vertical resize grip at a fixed height (the bundle sets `resize: none` only for a stretched one), so more input lines are a drag away; the `st.code` output does not follow, so that is a footnote, not a lever
- `streamlit_app.py` sets `TRANSFORMERS_VERBOSITY=error` via `os.environ.setdefault` at the top of the file, muting transformers' image-processor alias warnings that Streamlit's module watcher otherwise triggers on every rerun. **It mutes transformers' own logger only.** The same probe also makes Streamlit's watcher log tracebacks of its own, and nothing here silences those: transformers registers 218 alias modules named `transformers.models.<x>.image_processing_<x>_fast` in `sys.modules`, each with a module-level `__getattr__` that imports the real implementation, and `local_sources_watcher.get_module_paths` asks every module `hasattr(m, "__path__")` — which calls that `__getattr__`, which runs `import torch`, which raises `ModuleNotFoundError`, not the `AttributeError` the extractor swallows. The 109 torch-dependent aliases each log `Examining the path of … raised:` with a full traceback, ~195 KB in total, on the first rerun after `load_model`'s deferred `from mlx_lm import load` pulls transformers in — and again on any later rerun that imports a new module, because `update_watched_modules` rescans **all** of `sys.modules` whenever the set changes. Pre-existing and harmless: the watcher module is byte-identical between Streamlit 1.61.1 and 1.63.0 and the alias `_getattr` between transformers 5.14.1 and 5.17.0 (verified 2026-09-11 against the cached wheels), the noise goes to the terminal rather than the UI, and the aliases resolve to no watchable file either way. Deliberately not silenced with a logger level on `streamlit.watcher.local_sources_watcher`, which would also hide the watcher's real warnings
### Page layout and controls

The page runs at module level, top to bottom: title, the bordered language row, `warning_slot`, the two panels, the controls row — inside `with st.bottom:` since 2026-09-13, so it renders in Streamlit's sticky bottom bar rather than the page flow (see the controls-row bullet) — then the translate block. Until earlier on 2026-09-13 all of this sat inside `with text_tab:` under an `st.tabs` strip; the body was dedented in place when the tabs went, so the order and every mechanism below are unchanged.

- Language selectboxes use the flat `LANGUAGES` list (67 items) with collapsed labels and Streamlit's built-in type-to-search, in a **`[10, 1, 10]` from/swap/to row** inside `st.container(border=True)` — the page's only stroke, drawn around the pair of controls that describe the operation
- The selectboxes carry `on_change=clear_translate_output`, which drops a settled translation when either picker moves. The settled output is an unlabelled `st.code` block — no label, no caption, no provenance line — so changing To from French to German left the card asserting English → German above a panel still holding French, with Download still offering it. Only the output goes; `translate_input` stays so re-pressing Translate is one click, and `swap_languages` needs no hook of its own because it clears the output itself and Streamlit does not fire `on_change` for a programmatic session-state write
- The download name is captured into `st.session_state.download_name` at the moment the output settles, not built at the button: `target_lang` keeps moving afterwards, so a name read at render time describes the dropdown rather than the bytes. Two writers own that state, and only two: `settle_translate_output(text)` (the success path and the partial-failure path) and `clear_translate_output()` (picker moves, the empty-output path, the no-partial failure path, and the swap's delegate). The success and partial paths used to inline the settle pair, and the two reset paths the clear pair — two copies of the settle pair and three of the clear pair (the function plus both reset paths); the name format itself is the pure `settled_download_name(target_lang)`, unit-tested, so the f-string exists once. `AppTest` cannot verify it — `DownloadButton`'s proto has no `file_name` field, only a media-manager `url` — so the wiring is guarded at source level by `test_text_download_button_uses_the_recorded_name`
- Swap button (`:material/swap_horiz:`, `type="tertiary"`, `help=` tooltip) flips languages via `st.session_state` and moves a **settled** output into input, then delegates to `clear_translate_output` so "clear the settled translation" means one thing on both paths. The move is guarded on there being an output, since 2026-09-13: unguarded, a swap before anything had been translated assigned `""` over the typed draft — the one moment swap is most wanted (typed, pair backwards, not yet translated), reproduced with `AppTest` and pinned by `test_swap_keeps_typed_input_when_nothing_is_translated`. The moved text is also cut to `MAX_INPUT_CHARS`: `max_chars` is browser `maxlength`, and Streamlit's `TextAreaSerde` clips only widget and default values, so a programmatic write went in whole and a 30,500-character output landed in the input at full length; it is clipped the way the browser clips a paste, silently, and `test_swap_clips_a_long_output_to_the_input_cap` holds it (both tests fail against the unguarded body — checked). The clip is the pure `clip_to_input_cap`, and it counts **UTF-16 code units**, not characters, because that is what `maxlength` and Streamlit's frontend guard count (1.63.0's `useUpdateUiValue` drops any edit whose `value.length` exceeds `maxChars`): a plain `text[:MAX_INPUT_CHARS]` kept 30,000 emoji — 60,000 units — and a controlled textarea over `maxlength` rejects every single-key edit that leaves it there, so the input read as frozen until selected and replaced. It never splits a character; `test_swap_clips_in_the_browsers_units_not_characters` and three unit tests pin it. The tooltip says "Swap languages and move the translation into the input", because the plain "Swap languages" hid two destructive side effects (output wiped, input overwritten, not undoable)
- The swap button passes an **empty label**, which `best-practices.md` forbids in general — but `st.button` is the exemption: it has no `label_visibility`, its docstring omits the "never set an empty label" paragraph that 14 other widget docstrings carry, and `button.py` is not among the modules calling `maybe_raise_label_warnings`. Icon-only is Streamlit's own idiom here and there is no in-API alternative. The residual cost is real and unfixed: `DynamicIcon` renders the Material glyph as a `translate="no"` span with **no `aria-hidden`**, and `help=` becomes `aria-describedby` only while the tooltip is open, so the computed accessible name is the ligature text — a screen reader announces "swap_horiz, button"
- `warning_slot = st.empty()` is declared above the panels so the translation block (which runs later in the script) can place warnings above the input/output without needing `st.rerun()`. It is an **`st.empty()`, not an `st.container()`**, and the reason is a Streamlit mechanism worth knowing before putting a spinner in any empty container: since 1.53 (`PR #12826`) `st.spinner` is a *transient* element that arms a 0.5 s timer for its create message and sends its clear message **unconditionally** on exit. A warm `@st.cache_resource` load returns in microseconds, so `ensure_model`'s spinner never paints — but the clear still arrives, addressed to the slot's child 0, and the frontend appends it to a container as a childless node (`setNodeAtPath` appends when the index equals `children.length`). One child stops the block counting as empty (`isEmpty` is `children.length === 0`, and `st.container()` sets `allow_empty = False`), so a container that is otherwise not rendered at all was painted as a 0px flex item and the enclosing block's 16px `gap` wrapped it (the tab column's, when it was measured; the page body sits in the same kind of block now): measured 2026-09-12 in Chrome with a `MutationObserver`, both panels sat **16px lower from 178 ms after the click until the closing `st.rerun()` rebuilt the tree** — every click, not just the cold one — and after a cold load the spinner cleared but the phantom kept them there. The phantom lives exactly as long as the run, whichever way the run ends: a run that finishes with `st.rerun()` loses it to `clearTransientNodes` when the next run starts, and a run that finishes normally loses it to the end-of-run `clearStaleNodes` sweep (measured: gone the moment the run completed, in a variant with no rerun). An `st.empty()` has no child slots — its clear is addressed to the empty element's *own* path in the parent block, so the transient anchors onto the element already there, whose container is `display:none`: no phantom, and a spinner that does paint still clears cleanly. Verified with a 30-line A/B (container + instant spinner: 16px; no spinner: none; `st.empty()` + instant spinner: none) and unreported upstream — `PR #13849` (1.58) names the "unnecessary clear_transient messages" but fixed only a sibling stale-anchor symptom, and 1.63.0's `spinner.py` still sends the clear unconditionally. Holding one element costs nothing here: every writer is in an `if/elif` chain, and the `translate_notice` drain fires on the run *after* the one that set it. `test_spinner_slots_are_empty_elements_not_containers` derives every spinner receiver from the call sites — `warning_slot` is the only one now — and pins each to `.empty()`. The comment above `warning_slot` in `streamlit_app.py` is the code-side record of the mechanism; `ensure_model`'s docstring and the test point at it rather than restate it
- Side-by-side input/output panels. The input is a `st.text_area` capped at `MAX_INPUT_CHARS` (30,000); that cap reaches the browser as HTML `maxlength`, so an over-long paste is clipped with **no event the server can see**. The placeholder names the number, and **which limit binds depends on the script**. Measured with the model's own tokenizer: 30,000 characters of English prose is ~5,756 tokens, comfortably inside `MAX_INPUT_TOKENS`, so for Latin scripts the character cap is what a user actually hits — silently. The same 30,000 characters of Thai is ~24,897 tokens, so there the token gate fires first and announces itself with its own count. The placeholder covers the failure that has no other surface; the token gate covers itself

### Loading the model and running inference

- Translation model loads **lazily**: `@st.cache_resource(show_spinner=False) def load_model()` wraps `mlx_lm.load`, and `ensure_model(slot)` calls it from inside the translate handler — after the free empty-input and same-language checks, before the tokenizer is needed — rendering **both** the spinner and any failure into the slot it is handed -- `warning_slot`, an `st.empty()` for the transient-spinner reason under Page layout and controls -- and returning `None`. `show_spinner=False` on the decorator is load-bearing: the default paints the decorator's own "Running `load_model()`." spinner at the script cursor on a cache miss, which inside a translate handler is at the foot of the main block — reproduced on a cold cache, when the row was still in the flow, it sat under the buttons for the whole load, a second indicator at exactly the off-the-fold position `ensure_model`'s slot exists to avoid. The spinner has to go in the slot: inside a translate handler the script cursor is below the panels, at the foot of the main block, so a bare `st.spinner` put the only sign of activity below the fold while the error appeared at the top. `@st.cache_resource` is process-global (shared across every session and user, not per-session), so the load happens once per server process, and it does **not** memoize exceptions — a failed load leaves the button live and a later click retries. Loading eagerly at page load put the whole UI behind ~3.6 GB of weights: no language pickers, nothing to type into while it read. Consequently the translate button is **not** gated on a `model_loaded` flag — there is no cheap way to know the model loads without loading it, so a broken install surfaces on click, next to the action that caused it
- `tokenize_prompt` applies the chat template with `tokenize=True` and returns the prompt token ids — its `len()` gates against `MAX_INPUT_TOKENS`, and the same ids are passed to `stream_translate` so the prompt is tokenized exactly once per translation
- `stream_translate` takes pre-tokenized prompt ids, calls `mlx_lm.stream_generate` with `sampler=make_sampler(temp=)`, and yields the cleaned running result after each chunk
- `clean_model_output` strips whitespace and the `<|END_RESPONSE|>` token leaked by the model
- UI tests use `streamlit.testing.v1.AppTest`; mocks target `mlx_lm` because AppTest runs scripts via `exec()`; download buttons have no named accessor, so `at.get("download_button")[0]` is the page's one (the list held two, `[1]` the Document tab's, until 2026-09-13; `test_download_button_exists` pins the length at 1). The `clear_st_cache` autouse fixture clears `st.cache_resource` only — the `st.cache_data` clear went with `cached_document_chunks`, the one `cache_data` function the app had. Since Streamlit 1.63 (#16711) AppTest raises `AppTestError` on `set_value`/`click`/`upload`/`clear` against a **disabled** widget — `set_value` on the disabled empty-state output `text_area`, say — where 1.61 silently reran. No test does; the output panel is read-only (assert on `.value`)
### Page chrome

- The title has **no subtitle**. A one-line `st.caption` — "67 languages, translated on your Mac — nothing is sent to a server." — sat under it until 2026-09-12, worded "to a server" rather than "anywhere" so the announced model download (and, at the time, the Document tab's OCR-data download) would not contradict it. It was removed because the claim was **measured false**: `mlx_lm.load(MODEL_ID)` passes no revision, so `huggingface_hub`'s `snapshot_download` resolves `main` with `GET https://huggingface.co/api/models/<MODEL_ID>/revision/main` on the first Translate of **every fresh server process, warm cache included** (`snapshot_download`'s `repo_info` call, reached from `load(MODEL_ID)` through `mlx_lm`'s `_download`). The request carries the `hf_hub`/Python versions in its User-Agent and, whenever `~/.cache/huggingface/token` exists, the user's `Authorization: Bearer` token; at most daily it is preceded by an unauthenticated `GET /api/agent-harnesses` (huggingface_hub ≥ 1.19's dynamic harness registry — env-var harness detection itself dates from 1.9, and 1.31.0 is what is installed — gated by `HF_HUB_DISABLE_TELEMETRY`). Nothing on screen announces either — the spinner says "the first run downloads". Two independent probes agreed (an `HF_ENDPOINT` redirect to a local recording server, and an in-process patch of `httpx.Client.send`; huggingface_hub 1.x is httpx-only, so patching `requests` shows a false negative). It never carries user content — a bodiless GET built from constants before any text exists, and inference never touches `huggingface_hub` — so a claim about *data* would have been true where the claim about *the network* was not; removal rather than rewording was the choice made. `HF_HUB_OFFLINE=1` suppresses the request and the cached load still succeeds, ~0.3 s faster than online (the GET's latency; `load()` alone is ~0.9 s either way), but it would also fail the cold download the spinner promises, so it is not the fix. Two routes would stop the GET while keeping the cold download — a 40-hex `revision=` (which `snapshot_download` short-circuits before `repo_info`, and `mlx_lm.load` accepts) or a cache-first `local_files_only=True` load with a download fallback — and both also freeze the model against upstream pushes to `main`, so neither is taken; that is a product decision, recorded as open. ### Model and theme

- The app uses one model: `mlx-community/tiny-aya-global-8bit-mlx` (CC-BY-NC, non-commercial only)
- `.streamlit/config.toml` is the project's **own theme, "Reading Room"** — a warm-neutral ink-and-paper palette with one verdigris accent, dark-first, both modes stated in full. It replaced a restated copy of Streamlit's stock theme on 2026-09-11, which had itself replaced a hand-built Nord theme; both predecessors are in git history. **The comment block at the top of the file is the full record** — every value with its measured ratio, the derived states (hover, focus ring, caption, placeholders, borders, skeleton, status tints) emulated from the 1.63.0 bundle's own colour functions, and the alternatives rejected on the way — so cite it rather than duplicate it here; this section carries what an editor of *this* repo needs to not break it. What stating both modes earns is narrower than it looks: once a *custom* theme exists at all, Streamlit drops its built-in presets from the menu (`keepPresetThemes:!1`), and the System/Light/Dark radio in the ⋮ menu is rendered only when more than one theme is available (`if(t.length<=1)return[]`) — a lone `[theme]` yields a single internal `Custom Theme` and the radio disappears entirely, rather than showing a locked entry as an earlier version of this bullet claimed. Any key in **either** `[theme.light]` or `[theme.dark]` is enough to get the three-entry list (Custom Theme Light / Dark / Auto — the check reads `let t=bn(e.light),n=bn(e.dark),r=[];if(t||n)` in 1.63.0's `utils.Bid3C9ZE.js` — grep for `.light),n=` since the helper name moves; 1.61.1 had the same shape as `Iu`, and the missing side is derived from `[theme]` on the stock base), so stating both is this project's choice to spell out both palettes, not a Streamlit requirement — and here it is also how the two palettes stay designed rather than derived. A repo with **no** config at all still gets the full System/Light/Dark switch, so the file is not what earns the toggle — an earlier version of this bullet claimed it was, which is also wrong. While the file restated stock, deleting it would have been visually identical; it no longer would be
- **22 keys, all valid in Streamlit 1.63.0**: two type keys under `[theme]` (`headingFont = "serif"`, `codeFont = "sans-serif"`), twelve colours under `[theme.light]` and eight under `[theme.dark]`. Palette, as primary / background / secondaryBackground / text / link: light `#287160` / `#f8f5ef` / `#ebe5da` / `#0e0d0b` / `#287160`, dark `#33826f` / `#161412` / `#2f2b27` / `#e8e2d6` / `#5bae9b`. - `codeBackgroundColor` is pinned to `secondaryBackgroundColor` in both modes — under stock it was the **one deliberate departure**, and it survives the new palette unchanged, now guarded by `test_code_background_matches_secondary_background` (which compares normalised colours, so a case-only respelling cannot fail it). It is not cosmetic pedantry. The reason is **spatial, not temporal** — it used to be temporal, and that reason is now dead. The old one: the page streamed into `st.code` then swapped in a settled disabled `text_area`, so the panel changed shade the moment a translation finished. **That swap no longer exists** (settled output renders through `st.code` too), so do not go looking for it. One trap when emulating any bundle-derived colour: the bundle rounds with JS `toFixed()`, which takes `.5` ties **up**, where Python's `round()` is banker's and lands one 8-bit step low on every tie — the `bgMix` figures in `config.toml` were corrected for exactly that. `codeFont = "sans-serif"` is the typographic half of the same pin (see the type bullet below)

So a side was chosen, and it is the **button**: dark white-on-`#33826f` is **4.60:1** (the Translate label, passes), and `#33826f` on the page is **3.99:1** — which was the theme's one knowing AA text failure, the active tab label, named three times over (indicator, position, the content already showing under it). **As of 2026-09-13 the app renders no tab strip, so that 3.99 has no element to land on**: the palette now has zero AA text failures in either mode, the pair is recorded as the trade-off it was designed under rather than something painted today (`config.toml`'s ACCENT block says the same), and the button side would still be the right choice if a tab strip ever came back. Light needed no trade either way (5.80 button, 5.33 primary-on-page). Under stock the red was 3.30:1 under the white label in **both** modes and 3.30 as the light tab label — two knowing failures — and the button test had been lowered from 4.5 to 3.0 to admit it (an earlier bullet justified the 3 as SC 1.4.11, wrong twice over: 1.4.11 measures a component against the *adjacent* background, not its own label, and text inside a control is carved back out to 1.4.3). It is now **`test_primary_button_label_readable_in_both_modes`** with the **4.5 floor restored**. The admissible band is a **knife-edge**, because the same colour is the 1px focus border on the panels (3.05:1 dark, SC 1.4.11) and the label and the border pull L(primary) in opposite directions: ±1 on every RGB channel of the dark primary keeps both, **+2 drops the label to 4.48, −2 drops the focus border to 2.97**. Re-run the helpers (`_relative_luminance` / `_contrast_ratio` / `_composite` in `test_streamlit_app.py`) before changing a digit of `primaryColor`, `backgroundColor` or `secondaryBackgroundColor`; the ACCENT block in `config.toml` carries every measured pair and the alternatives rejected. Seven theme tests make it durable: the label test above; `test_primary_focus_border_clears_non_text_floor` (primary on `secondaryBackgroundColor` ≥ 3.0); `test_primary_on_page_does_not_regress` (primary on `backgroundColor` ≥ 3.5 — a regression guard against an accent that fades into the page, not a standard being met; it was `test_active_tab_label_does_not_regress` until 2026-09-13 and was renamed, floor and history intact, when the tab label it was named for stopped existing — kept as a palette guard, not dropped); `test_caption_readable_in_both_modes` (the 0.6 composite ≥ 4.5); `test_code_background_matches_secondary_background`; `test_theme_fonts_are_bundled_not_fetched` (walks every nested table and `base`); and `test_usage_stats_are_off`. The helpers normalise through `_hex6`, so a `#rgb` short form or an upper-case respelling — both valid to Streamlit — cannot crash a ratio test or fail a guard on spelling alone. What the button side costs is stated, with numbers, in `config.toml`: the selected tab was dimmer than the inactive ones and carried on chroma and the indicator (moot without a tab strip); the hover fill sinks toward the dark page rather than lighting (move the pointer off before a screenshot); the 50%-alpha focus ring fails the 3:1 non-text floor in both modes exactly as stock's did, and the 1px primary border is the cue that does clear it on the text areas and selectboxes; on the primary button itself `:focus-visible` shows only as the fill sinking, which is Streamlit's primary-button styling under any theme, not a cost of this accent
- `test_link_text_readable_in_both_modes` still demands a genuine 4.5:1 — its floor was not touched, only its comment, to note why the dark link is not the primary — and it is why dark `linkColor` is **split from the primary**: `#5bae9b` (the accent's text weight, same hue) is 6.98:1 on the page, where the button-side `#33826f` would sit at 3.99 and fail the test outright. Light keeps `linkColor == primaryColor`. The app paints no links today; the key exists to keep a future one on-palette. The old escape hatch this bullet carried — red90 / red100 for an AA primary without leaving Streamlit's own palette — is moot now that the palette is the project's own
- **Two type keys, zero network fonts.** `headingFont = "serif"` sets the title — the page's only heading, and the only thing on it that can carry an identity — in Source Serif, bundled in the Streamlit wheel and served by the local server (the Roman woff2 is 429 KB, the largest asset the theme adds). `codeFont = "sans-serif"` sets the output `st.code` in Source Sans: the input `text_area` is `fontSizes.sm = 0.875rem` and the code block's inner `<code>` is `codeFontSize = 0.875rem`, so the two panels already matched at 14px and this one key makes translated prose read in the same face and size as the prose it came from — the panel is `st.code` only because that element can be replaced mid-stream and copied; its monospace was a side effect. `codeFontSize` is **deliberately unset**: anything larger than the default makes the output bigger than the input. Line heights and padding still differ (12px at 1.4 in the input, 16px at 1.6 in the code block — the first lines sit ~3px apart) and no theme key reaches either; that is geometry, not a theme bug. The bundle maps the generic names itself, so no `[[theme.fontFaces]]` block is needed, and `test_theme_fonts_are_bundled_not_fetched` fails on a `fontFaces` key in any table, a `://` in any `*Font` value (sidebar tables included), or a remote `base` — the README's privacy promise makes a Google Fonts URL, which fires on every page load, a hard no. `baseFontSize` is untouched at Streamlit's 16px, so the historical `baseFontSize = 14` measurements flagged under Page layout and controls are still historical
### Lint and type checking

- Ruff lint selection is `["E", "F", "I", "W", "UP", "B", "SIM"]` — pycodestyle, pyflakes, isort, pyupgrade, bugbear, and simplify
- `ty check` covers the whole project; the `at.get(...)` assertions in `test_streamlit_ui.py` carry inline `# ty: ignore[unresolved-attribute]` because `.get()` returns `Element | Block` and these widgets have no typed accessor to narrow to. **Three kinds need it**, not just download buttons: `get("download_button")` (six sites), `get("code")` (two), and `.ignore_rerun` on a button (one) — nine lines in all, re-derived 2026-09-13; `get("file_uploader")` was a fourth kind until the Document tab went. Scoped to those lines so the rule still catches typos elsewhere in the tests
- A test that references a `@st.cache_data`- or `@st.cache_resource`-decorated function as `streamlit_app.<name>` needs **no** `# ty: ignore` — the editor's incremental LSP flags it `unresolved-attribute` (the decorator trips it), but the `ty check` CLI (the gate) resolves it fine, so adding an ignore would make the CLI fail with `unused-ignore-comment`. Trust the CLI, not the editor squiggle. Learned on the `cached_document_chunks` tests, gone with the Document tab on 2026-09-13; no surviving test references a decorated function, so the trap is only recorded here
