## Project

Streamlit application for translation using Cohere Labs Tiny Aya Global on Apple Silicon with MLX. The app translates text and documents across 67 languages with local inference via the `mlx-community/tiny-aya-global-8bit-mlx` model.

## Stack

- Python 3.13+ with uv for project management
- Streamlit for UI
- watchdog for Streamlit's file watcher, listed in `dependencies` **explicitly** because Streamlit's own requirement on it is gated `sys_platform != 'darwin'`. On macOS Streamlit therefore ships *without* it and falls back to `PollingPathWatcher`, which is what prints "For better performance, install the Watchdog module" on every launch. Streamlit's accompanying `xcode-select --install` hint is stale — the macOS wheel (`cp313-cp313-macosx_11_0_arm64`) is a compiled FSEvents binding but is **prebuilt** on PyPI, so nothing is built locally. It belongs in `dependencies` rather than the `dev` group because the server process imports it, not the tests. Confirm it took with `uv run python -c "from streamlit.watcher import path_watcher; print(path_watcher.get_default_path_watcher_class().__name__)"` → `EventBasedPathWatcher`
- mlx-lm for translation inference on Apple Silicon
- liteparse for parsing uploaded documents (required dependency: one ~12 MB abi3 wheel with no transitive deps, 26 MB installed)

## Structure

- `streamlit_app.py` — main app: config, pure functions, Streamlit UI
- `test_streamlit_app.py` — pytest unit tests for pure functions
- `test_streamlit_ui.py` — pytest UI tests for Streamlit interface
- `.streamlit/config.toml` — the project's own theme ("Reading Room"), dark-first, both modes stated in full; the comment block at the top of the file is the full record of every value and measured ratio, so cite it rather than duplicate it; see Model and theme. Also carries `[browser] gatherUsageStats = false`; see Page chrome
- `assets/favicon.svg` — the local favicon (the Material `translate` glyph in the accent), inlined as a `data:` URL by `set_page_config`; a test asserts it resolves. See Page chrome
- `.github/workflows/` — `ci.yml` (checks + auto-publish release) and `release.yml` (manual bump), sharing `.github/scripts/release-notes.sh`; see Automation and Releases
- `.claude/settings.json` — ruff/actionlint/ty/pytest hooks and the protected-path guard; see Automation
- `assets/screenshot.png` — README hero image; see Screenshots

## Commands

```bash
uv sync                                                      # install dependencies
uv run streamlit run streamlit_app.py                        # run the app
uv run pytest -v                                             # run tests
uv run pytest -k chunk_text -q                               # one topic
uv run pytest test_streamlit_app.py::test_buttons_use_width_stretch  # one test
uv run ruff check --fix .                                    # lint
uv run ruff format .                                         # format
uv run ty check                                              # type check
```

When working with Python, invoke the relevant `/astral:<skill>` for uv, ty, and ruff to ensure best practices are followed.

- Bare `python` is **not** on `PATH` (`command not found: python`); everything goes through `uv run`, one-off scripts included (`uv run python <script>`)
- `uv run streamlit docs st.<command>` prints the exact signature and docstring from the *installed* Streamlit — use it instead of recalling an API from memory. The `developing-with-streamlit` skill routes to version-matched reference docs bundled inside the venv at `.venv/lib/python3.13/site-packages/streamlit/.agents/skills/`, not to anything in this repo; that tree also carries ready-made theme configs under `assets/templates/themes/configs/` (12 presets, `nord.toml` among them)
- A throwaway `uv run python -c` that **imports** `test_streamlit_app` or `streamlit_app` buries its output under dozens of `missing ScriptRunContext!` warnings, because importing the app runs Streamlit calls outside a script run. For a quick calculation, inline the few lines you need rather than importing the module

## Automation

- CI (`.github/workflows/ci.yml`) has **two jobs**. `check` runs on `macos-latest` (Apple Silicon, so `mlx-lm` installs natively) for pushes to `main` and PRs: `uv sync --locked`, `ruff format --check .`, `ruff check .`, `ty check`, then `pytest -q`. Note `--check` — unformatted code fails CI rather than being auto-fixed. `release` is the auto-publish job described under Releases
- The test step is **bare `pytest`**, not the hand-listed pair it used to be. `pyproject.toml` sets `testpaths = ["."]`, so collection follows the repo — naming the two files meant a third test module could be added to a green CI that never ran it, and the same list was duplicated in the `Stop` hook, `release.yml`, the README, and this file. Confirmed identical coverage: 163 tests collected either way (re-checked 2026-09-11 after the theme pass added five; it was 158 before)
- Both jobs carry **`timeout-minutes`** (30 on the macOS `check`, 10 on the ubuntu `release`; `release.yml` also 30). GitHub's default is **6 hours**, and macOS bills at 10x — so an unguarded wedged run costs ~3,600 billed minutes. This is the same cost concern that put the `release` job on ubuntu, applied at the point of largest exposure
- `.python-version` is **tracked, deliberately** — it is the only thing pinning CI's interpreter. It was previously gitignored alongside `.env`/`.venv/`, so a fresh clone (which is every CI run) left uv with nothing but `requires-python = ">=3.13"` and it resolved the newest match; CI would have silently moved to 3.14 on release day. It also makes README's "uv installs a matching interpreter from `.python-version`" true, which it was not while the file was untracked
- Actions are pinned to `actions/checkout@v7` and **`astral-sh/setup-uv@v9.0.0`** — note the exact patch version on the second one, and **do not shorten it to `@v9`**. setup-uv stopped publishing floating major and minor tags after `v7.6`: its v8.0.0 release removed the workflow that maintained them, so the tag list runs `v7.6.0`, `v7.6`, … `v8.0.0`, `v8.1.0`, … `v9.0.0` with **no bare `v8` or `v9` ref at all**. `@v9` fails the run in ~6 s with `Unable to resolve action ... unable to find version`, *before any job starts* — which also means `release` is skipped by `needs: check` and nothing is tagged. This was shipped and failed once; the release-note line that caused it ("Remove update-major-minor-tags workflow") reads like internal housekeeping and is not. `actions/checkout` **does** still publish major tags, so `@v7` there is correct. Verify a pin with `gh api repos/<owner>/<repo>/git/ref/tags/<tag>` rather than reading a version off `releases/latest`, which reports `v9.0.0` whether or not `v9` exists
- Checked before bumping from v4/v5 in August 2026: checkout v5-v7 are node24, a credentials-file change, and a fork-PR block that only affects `pull_request_target`/`workflow_run` (neither used here); setup-uv v7-v8 are node24 plus internal removals. **setup-uv v9 deliberately increases Actions cache usage** — flagged as breaking by upstream for that reason, so watch cache storage if it ever matters
- The sync is `uv sync --locked`, not a bare `uv sync`. `uv.lock` records the project's own version, so a hand bump that edits `pyproject.toml` alone leaves the lock stale — and a bare `uv sync` **rewrites it in place and goes green**, which would let the `release` job tag a commit whose lock disagrees with its pyproject. `--locked` fails the run instead. The same swap was made in `release.yml`, which claims "same gate as ci.yml" and now actually is
- `concurrency` is declared **per job**, not at workflow level. A workflow-level `cancel-in-progress: true` cancels the *whole run*, so a second push landing during a release could kill the job between `git push --tags` and `gh release create`, leaving a pushed tag with no release. `check` keeps `ci-${{ github.ref }}` / cancel-in-progress; `release` takes `group: release` / **no** cancel, the same group `release.yml` uses, so the two release paths serialize against each other repo-wide
- `.claude/settings.json` carries **four** hooks, and three of them encode a trap worth knowing:
  - `PostToolUse` → **ruff** on `*.py` edits only (whole project, so edited files may be reformatted underneath you). The two commands are deliberately **not** chained with `&&`: `ruff check --fix` exits 1 whenever unfixable violations remain, which skipped `ruff format` on precisely the files that needed it — verified by reproduction, an unformatted `x    =   undefined_name` survived the chain untouched. It runs `check --fix .; rc=$?; format .; exit $rc`, so formatting always happens and the lint status still propagates
  - `PostToolUse` → **actionlint** on `.github/workflows/*.y{,a}ml` edits, `exit 2` on findings. It redirects **stdout to stderr** (`actionlint "$f" >&2`) because actionlint reports on stdout (measured: 583 bytes stdout, 0 stderr) while Claude Code surfaces only *stderr* on `exit 2` — without the redirect a broken workflow fired the hook correctly and reported nothing
  - `Stop` → `ty check` + `pytest`, unconditional. It runs on docs-only sessions too; that is the accepted price of not letting a heuristic skip the run that mattered — and the price is small enough to be worth stating rather than re-guessing: 6.88 s for the 163 tests, 1.2 s for `ty check` (re-measured 2026-09-11 on ty 0.0.80, after the five theme tests landed; the 158-test suite ran in 6.5 s the same day)
  - `PreToolUse` → the fail-closed guard. Blocks edits to `uv.lock` and `.streamlit/secrets.toml`, and blocks hand-editing `version` in `pyproject.toml` (use `uv version --bump`, which rewrites the lock as well). It reads stdin **once** into a variable — `jq` consumes stdin, so the second query for `.tool_input.new_string` would otherwise return empty and the guard would silently pass everything. Its version regex is anchored (`^[[:space:]]*version[[:space:]]*=`) so `target-version = "py313"` under `[tool.ruff]` stays editable; without the anchor no ruff config change would be possible

## Releases

- Versioned with SemVer in `pyproject.toml` (`version`); currently pre-1.0 (0.x). First tagged release was `v0.8.2`. Tags carry a `v` prefix; `pyproject` stays bare
- There are **two** ways to cut a release, and both **publish immediately**. There is no draft and no review step: the release goes live, watchers are notified, and the README's release badge moves the moment the job finishes. Deleting a release afterwards does not unsend the notification, so the review that used to happen on the draft has to happen *before* the push — in the commit subjects, which are now the notes:
  - **`Release` workflow** (`.github/workflows/release.yml`), run from the Actions tab with a `patch`/`minor`/`major` choice. It runs the full CI gate, bumps the version, generates notes, commits, tags, pushes, and publishes. This is the path that *performs* the bump, and `uv version --bump` is the reason to prefer it
  - **CI's `release` job** (`.github/workflows/ci.yml`), which publishes a release for any version bump that lands on `main` by hand. Bump `pyproject.toml` + `uv.lock`, commit, push — the tag and the published release follow automatically
- Both publish steps pass **`--verify-tag`**, which is not redundant with the tag push in the step above it. `gh release create` *creates* a missing tag itself, resolving it against the default branch's HEAD — so a tag push that failed silently would produce a live release attached to the wrong commit. With the flag the step aborts instead, leaving the tag and release consistent. `--latest` is deliberately unset, which is **not** the same as passing it: unset means GitHub picks the Latest release automatically from date and version, which is right while the newest release is always the highest version. Each step captures `gh`'s stdout (the release URL) into `$GITHUB_STEP_SUMMARY`, because with nothing to review in the Releases tab the run summary is where the link is wanted
- The two cannot double-release, for **two independent reasons**, and the first is the same GITHUB_TOKEN rule that shapes `release.yml`: the bump commit it pushes is authenticated with `GITHUB_TOKEN`, so it does not start a CI run *at all*. Even if it did, CI's gate skips any version that is already tagged — which `release.yml` has done by then. They also share the `release` concurrency group, so they cannot interleave
- CI's gate is **"pyproject declares a version with no tag"**, deliberately not a diff against the parent commit. A push can carry many commits, a re-run would fire twice, and a force-push has no useful parent; the tag check is idempotent and answers the same question. It reads the remote (`git ls-remote --exit-code --tags origin`), which is the real source of truth for "has this shipped"
- CI's `release` job runs on **`ubuntu-latest`**, not the `macos-latest` the checks need — it is plain `git` + `gh`, and macOS runners bill at 10x. It reads the version with the runner's preinstalled `python3` + stdlib `tomllib` rather than `uv version`, the project's usual route: `uv` performs interpreter discovery and would download a whole Python to read one TOML field, on **every** push to `main` including the ones with nothing to release
- Its `permissions: contents: write` is declared **at the job**, overriding the workflow-level `contents: read`. The `check` job stays read-only
- There is no artifact to publish: `pyproject.toml` has no `[build-system]` and `uv.lock` records the project as `source = { virtual = "." }`. A "release" here is only a tag plus a GitHub Release
- The workflow bumps with `uv version --bump <part>`, which rewrites `pyproject.toml` **and** re-locks `uv.lock` in one command — a version bump touches **two** files, because the lock records the project's own version. Bumping by hand and forgetting the lock leaves it to be rewritten by the next `uv` command, potentially after tagging
- Release notes are generated from **conventional commits** since the previous tag, grouped into Features / Fixes / Performance / Refactoring / Documentation (`chore`/`test`/`ci`/`build` are omitted as noise; the compare link covers them). GitHub's own `--generate-notes` is useless here — it aggregates merged PRs, and commits land directly on `main`. That output now ships **unreviewed**, so a commit subject is user-facing copy the moment it is pushed. The hand-written Highlights/Requirements/Run blurb that the draft existed for is gone; if it is ever wanted back it belongs in `release-notes.sh` as a static footer shared by both paths, **not** as a restored draft on one of them
- That generator lives in **`.github/scripts/release-notes.sh`**, called by both workflows so they cannot drift into describing the same commits differently. It takes the output path as `$1` and `VERSION`/`REPO_URL` from the environment, and must run **before** the new tag exists or `git describe --tags --abbrev=0` returns the tag being created and the range collapses to nothing. It runs on **both** runner OSes, and macOS ships **bash 3.2**, so no bash-4 syntax: no arrays, no `${x,,}`. That is why the empty-range (first-release) case is spelled as two separate `git log` calls instead of an interpolated `$range` — the empty form needs an unquoted expansion, and bash 3.2 has no safe empty array. `set -o pipefail` is on, so each `section` needs its `|| true`: `grep` exits 1 for a commit type absent from the range, which would otherwise fail the run
- The workflow is `workflow_dispatch`, **not** tag-triggered, and that is deliberate: a tag pushed with `GITHUB_TOKEN` does not trigger other workflows, so an `on: push: tags:` release job would silently never fire
- Every `${{ }}` value is passed through a step-level `env:` block rather than inlined into a `run:` script — the standard defense against workflow command injection. `github.ref_name` is a branch name and must never be inlined
- `main` has no branch protection or rulesets, which is what lets the workflow push the bump commit directly. Adding protection means allowlisting the Actions actor
- Hand-bumping is now a **supported path rather than a fallback**: `uv version --bump <part>` → commit `pyproject.toml` + `uv.lock` **together** → push to `main`, and CI tags and publishes the rest. Do not tag by hand as well; the gate would then see the tag and skip, leaving no release. If CI is bypassed entirely, the fully manual sequence is still bump → commit both files → `git tag -a vX.Y.Z` → `git push origin vX.Y.Z`, and tags must be pushed explicitly — a branch push (including via GitHub Desktop) does not carry them, verify with `git ls-remote --tags origin`
- Committing the two files **separately** is the one way to get a wrong result: pushing a `pyproject.toml` bump without its `uv.lock` fails `uv sync --locked` in `check`, and `release` never runs (`needs: check`) — which is the intended outcome, but the release simply does not appear rather than announcing why. The failing step names it

Regenerate it whenever the theme or that tab's layout changes. Expect the PNG to read warm and brown-tinted against GitHub's cool `#0d1117` README ground: that is the palette, not a colour-management fault. Every trap below produces a plausible-looking but wrong image, which is why they are worth writing down.

- Serve it on a **free port**: `uv run streamlit run streamlit_app.py --server.port 8502 --server.headless true`. 8501 on this machine is usually another project's app, and Streamlit will happily start on a different port without saying so loudly. Note that `--server.headless true` is the one flag that makes the *server* reach out: `bootstrap.py` calls `net_util.get_external_ip()` (a GET to `checkip.amazonaws.com`) to print the "External URL" line, only in headless mode — the documented run command does not pass it, so a user's launch makes no such request
- The shot needs a **real translation**, not an empty app — but the old reason for saying so is gone. It used to be that the output `text_area` was `disabled=True`, so genuine output rendered in the same muted grey as placeholder text; settled output now goes through `render_output`/`st.code` and reads at full contrast, and the empty-state placeholder is `Translation appears here`. Weights are already in `~/.cache/huggingface` (~3.6 GB — `du -sh` prints `3.3G` because it reports GiB; the rest of the repo quotes 3.6 GB and that is the same number), so the Translate click costs seconds rather than a download
- **Move the pointer off the button before capturing — and off the page content altogether.** Clicking Translate leaves the cursor hovering it, and Streamlit's primary hover is darken-15% of the primary (the hex and its ratios are in `config.toml`'s ACCENT block; under stock it was `rgb(255,0,0)` against `rgb(255,75,75)`). It matters more now than it did: the hovered fill sinks toward the dark page rather than lighting, so a hovered Translate reads *pressed-in*, and a baked-in hover state reads as a deliberate colour choice, not a mistake. Verify with `getComputedStyle(btn).backgroundColor`, not by eye. The **cursor itself is rendered into captures** — a first attempt on 2026-09-11 had it sitting over the output panel — so park it at the far bottom-right of the viewport, outside the region being captured, not merely off the button
- Hide the Streamlit toolbar (`[data-testid="stToolbar"]`, plus `stDecoration`/`stStatusWidget`) by setting `display:none` from the page, and **re-hide after every rerun** — a translation rebuilds the DOM and brings it back
- macOS `screencapture` **does not work from this environment** — `could not create image from rect` for every region *and* every `-D` display, because the process has no Screen Recording permission and only the user can grant it. Do not burn time debugging the rect; use the Chrome extension
- The Chrome `computer` **`screenshot`** action downsamples (a 1080px-wide viewport returned 883px for the 2026-08 capture and 875px on 2026-09-11 — the factor is not fixed, so read it off the returned frame each time; it was 1.234 this time), while the **`zoom`** action re-renders its region at *native* resolution. `zoom`'s `region` is expressed in the **downsampled screenshot's** coordinate space, not viewport space — scale viewport coords by the downsample factor first. Out-of-range values fail with a message that misleadingly quotes the viewport size, which sends you looking in the wrong place
- **The main display cannot frame the shot.** The 1920×1080 display gives at most a 783px-tall viewport once the Dock and Chrome's own UI are subtracted (the window clamps at 960px tall), and the hero framing needs ~830px. The 2026-09-11 capture moved the window to the portrait 1080×1920 display with AppleScript — `tell application "Google Chrome" to set bounds of window N to {...}` — captured at a 1080×1693 viewport, and moved it back. Resizing in place on the main display cannot get there; do not try to shrink the framing instead
- **Sample the pixels first; convert only if they are off.** The gate is the byte-exact check, not the presence of a profile: open the capture with PIL and read the page (`#161412`), both panels (`#2f2b27`) and the Translate fill (`#33826f`, sampled at the fill, not the glyph). If they match, save as-is. If they are off, the capture is in display space and needs `PIL.ImageCms.profileToProfile(img, src, ImageCms.createProfile("sRGB"))` — with `src` the embedded profile when `im.info.get('icc_profile')` has one, and the display's own profile when the PNG is untagged — the `<Display>-<UUID>.icc` under `/Library/ColorSync/Profiles/Displays/` (ColorSync Utility → Devices shows which one is current; `system_profiler SPDisplaysDataType` only names the display, and a display can have more than one file there), because Chrome can return display-space pixels *without* tagging them on a wide-gamut screen. An untagged capture is therefore not evidence of sRGB, and converting an already-exact image against a display profile would be just as wrong. History: the 2026-08 capture was tagged with Chrome's `Google/Skia/…` profile and read `#101216` against the configured `#0e1117` until converted, after which the neutrals landed byte-exact and the saturated primary clipped ~4% (`#ff4b4b` → `#f54b4c`) **identically under all four rendering intents** — that residue was the red sitting *outside the display gamut*, not a floor of the round trip; `#33826f` is in gamut. The 2026-09-11 capture came back untagged and already byte-exact, so no conversion ran. The saved PNG carries an sRGB profile either way, embedded on save
- Sample the *fill*, not the centre, when spot-checking a button — dead centre is the label glyph, and white-on-fill anti-aliasing returns a washed-out tint (a pink, under stock's red) that looks like a colour bug
- Pin the theme before capturing: `localStorage.setItem('stActiveTheme-/-v2', '"Dark"')` then reload. The key is versioned (`-v2`), and leaving it at `"System"` means an OS appearance change mid-session silently reshoots in light
- Buttons now carry icons, so `button.innerText` is `"translate|Translate"` — selecting a button by its label text fails. Use the key-derived class Streamlit emits, `.st-key-translate button`
- The 2026-09-11 regeneration confirmed the checks worth keeping, with the values they now take: the neutrals land **byte-exact** (`#161412` page, `#2f2b27` both panels) and so does the button fill, `#33826f` sampled at the fill rather than the glyph, with **zero clip residue**. Under stock the same checks read `#0e1117` / `#262730` after the sRGB conversion, and the primary clipped to `#f54b4c`. Both panels reading the same value is also a live check on the `codeBackgroundColor` pin — the input `text_area` and the output `st.code` are the same shade side by side, which is the whole point of it — and the sans output panel is the live check on `codeFont`

## Conventions

Grouped for retrieval only — the headings below were inserted without reordering
anything, so two bullets sit under a neighbour rather than a perfect fit: the

model-ID bullet heads the theme group.

### Module layout and config

- Pure functions are defined above `import streamlit` with deferred imports for `mlx_lm` and `liteparse` inside their bodies, so tests can patch them without loading the model stack
- Config is hardcoded as module-level constants (`MODEL_ID`, `DEFAULT_TEMPERATURE`, `DEFAULT_MAX_TOKENS`, `MAX_INPUT_TOKENS`, `MAX_CHUNK_TOKENS`, `MAX_INPUT_CHARS`, `DOCUMENT_TYPES`, `MAX_UPLOAD_MB`) at the top of `streamlit_app.py`, plus shared UI constants (`PANEL_HEIGHT`, `SAME_LANGUAGE_WARNING`, `NO_OUTPUT_WARNING`) reused across both tabs; source-level tests guard against re-inlining `height=450` or duplicating either warning literal
- `streamlit_app.py` sets `TRANSFORMERS_VERBOSITY=error` via `os.environ.setdefault` at the top of the file, muting transformers' image-processor alias warnings that Streamlit's module watcher otherwise triggers on every rerun. **It mutes transformers' own logger only.** The same probe also makes Streamlit's watcher log tracebacks of its own, and nothing here silences those: transformers registers 218 alias modules named `transformers.models.<x>.image_processing_<x>_fast` in `sys.modules`, each with a module-level `__getattr__` that imports the real implementation, and `local_sources_watcher.get_module_paths` asks every module `hasattr(m, "__path__")` — which calls that `__getattr__`, which runs `import torch`, which raises `ModuleNotFoundError`, not the `AttributeError` the extractor swallows. The 109 torch-dependent aliases each log `Examining the path of … raised:` with a full traceback, ~195 KB in total, on the first rerun after `load_model`'s deferred `from mlx_lm import load` pulls transformers in — and again on any later rerun that imports a new module, because `update_watched_modules` rescans **all** of `sys.modules` whenever the set changes. Pre-existing and harmless: the watcher module is byte-identical between Streamlit 1.61.1 and 1.63.0 and the alias `_getattr` between transformers 5.14.1 and 5.17.0 (verified 2026-09-11 against the cached wheels), the noise goes to the terminal rather than the UI, and the aliases resolve to no watchable file either way. Deliberately not silenced with a logger level on `streamlit.watcher.local_sources_watcher`, which would also hide the watcher's real warnings
### Text tab and shared controls

- Language selectboxes use the flat `LANGUAGES` list (67 items) with collapsed labels and Streamlit's built-in type-to-search. Both tabs now carry the **same `[10, 1, 10]` from/swap/to row** inside `st.container(border=True)`. The Document card holds a **second** row — the uploader and its OCR notice — because describing a document source is one operation; leaving them as separate full-width siblings drew the tab's only stroke around its least consequential third (two dropdowns) while the control that must be acted on first had no grouping at all
- The Text tab's selectboxes carry `on_change=clear_translate_output`, which drops a settled translation when either picker moves. The settled output is an unlabelled `st.code` block, so changing To from French to German left the card asserting English → German above a panel still holding French, with Download still offering it. The Document tab deliberately answers this the *other* way — it keeps the output and discloses the real pair in `doc_meta` — because it has a provenance surface to disclose into and the Text tab does not
- The Text tab's download name is captured into `st.session_state.download_name` at the moment the output settles, not built at the button: `target_lang` keeps moving afterwards, so a name read at render time describes the dropdown rather than the bytes. Same reasoning as `record_document_provenance`. `AppTest` cannot verify it — `DownloadButton`'s proto has no `file_name` field, only a media-manager `url` — so the wiring is guarded at source level by `test_text_download_button_uses_the_recorded_name`
- Swap button (`:material/swap_horiz:`, `type="tertiary"`, `help=` tooltip) flips languages via `st.session_state` and moves output into input. **Both tabs have one now** — `swap_doc` calls `swap_doc_languages`, which flips languages *only*: a document's source is an uploaded file, so there is nothing to move the output into, and `doc_output` is left alone because the upload has not changed and `clear_doc_output` owns that invalidation. The tooltip says "Swap languages and move the translation into the input" on the Text tab, because the plain "Swap languages" hid two destructive side effects (output wiped, input overwritten, not undoable)
- The swap buttons pass an **empty label**, which `best-practices.md` forbids in general — but `st.button` is the exemption: it has no `label_visibility`, its docstring omits the "never set an empty label" paragraph that 14 other widget docstrings carry, and `button.py` is not among the modules calling `maybe_raise_label_warnings`. Icon-only is Streamlit's own idiom here and there is no in-API alternative. The residual cost is real and unfixed: `DynamicIcon` renders the Material glyph as a `translate="no"` span with **no `aria-hidden`**, and `help=` becomes `aria-describedby` only while the tooltip is open, so the computed accessible name is the ligature text — a screen reader announces "swap_horiz, button"
- `warning_slot = st.container()` is declared above the panels so the translation block (which runs later in the script) can place warnings above the input/output without needing `st.rerun()`
- Side-by-side input/output panels. The input is a `st.text_area` capped at `MAX_INPUT_CHARS` (30,000); that cap reaches the browser as HTML `maxlength`, so an over-long paste is clipped with **no event the server can see**. The placeholder names the number, and **which limit binds depends on the script**. Measured with the model's own tokenizer: 30,000 characters of English prose is ~5,756 tokens, comfortably inside `MAX_INPUT_TOKENS`, so for Latin scripts the character cap is what a user actually hits — silently. The same 30,000 characters of Thai is ~24,897 tokens, so there the token gate fires first and announces itself with its own count. The placeholder covers the failure that has no other surface; the token gate covers itself
- Output is rendered into an `st.empty()` placeholder (`output_placeholder`) so streaming can replace it progressively. The **settled** state goes through `render_output` too, exactly like the Document tab; the disabled `text_area` survives only as the *empty* state, where it supplies the placeholder (`Translation appears here` — an instructional phrase, because a bare noun in the same muted grey was indistinguishable from a one-word translation) and balances the input panel. It used to render the settled value, and Streamlit paints disabled content at `fadedText40`: measured **2.17:1 light and 3.53:1 dark** under the stock theme, i.e. the finished translation was *less legible than its own placeholder*, and a disabled textarea is unselectable, so it could not be copied at all — only downloaded. On the Reading Room palette that same token is **2.57:1 light and 3.03:1 dark** (`#938f87` / `#79746d` over the panels) — still the empty-state placeholder's colour, under 4.5:1 in both modes and in light under even the 3:1 non-text floor, which is accepted because disabled text is exempt and it is read once. The settled `st.code` reads at full contrast (`bodyText`, 10.88:1 dark / 15.50:1 light on the panel) and, since the theme's `codeFont = "sans-serif"`, in **Source Sans at 14px** — the same face and size as the `text_area` beside it, so the translated prose no longer switches to monospace the moment it settles
- Streaming fills the placeholder via the `render_output(placeholder, text)` helper — `st.code(..., language=None, wrap_lines=True, height=PANEL_HEIGHT)`, not `text_area` — repeating a widget call in the same script run would collide on the auto-generated element id, but `st.code` is non-widget and replaces freely; both tabs render output through this one helper
- Translate button (`type="primary"`, `width="stretch"`) uses a callback + flag pattern (`_do_translate`); after streaming, the translate block calls `st.rerun()` so the disabled output `text_area` and download button re-render with the final value
- Translate block validates input (`tokenize_prompt` + `MAX_INPUT_TOKENS` check) and wraps streaming in `try/except` (errors → `warning_slot.error`, empty output → `warning_slot.warning`)
- Download button (`type="secondary"`, `width="stretch"`) uses `st.download_button` to save the translation as `translation.txt`. The Document tab's equivalent is named from the upload instead — `document_download_name` gives `report.pdf` + French → `report-French.md`, because every output being `translation.md` left `translation (1).md`, `translation (2).md` with nothing to tell them apart. It splits on the *last* dot and leaves a dotless or dot-leading name intact
- Controls row is `st.columns(2)`, mirroring the side-by-side input/output panels — **not** `st.container(horizontal=True)`, even though Streamlit's own best-practices doc prefers horizontal containers for button rows. The container's children are `flex: 1 1 fit-content`, so a stretched button grows from its *intrinsic* width and the row ends up content-proportional rather than 50/50: measured in-browser, Translate 460.6px against Download's 465.4px, versus the panels' 461/461 directly above, and a 14px gap against their 16px. Columns are a proportional grid, which is what mirroring the panels needs. **Those figures are historical** — they were measured under the old theme's `baseFontSize = 14`, and the theme now inherits Streamlit's 16px base, which shifts every intrinsic width and gap. The conclusion survives (a flex row is content-proportional, a column grid is not); the specific pixels do not, so remeasure before citing them. Streamlit 1.63 (#16578) added a second way the two rows differ: a button placed *directly* in a column now resolves `wrap=None` to a single-row label truncated with an ellipsis (`white-space: nowrap`), the rule a horizontal container always had, while a button inside a nested container keeps wrapping. Translate, the Text tab's Download and Translate document are direct column children and pick that up; `download_doc` renders through `doc_download_col.container()` and does not. Nothing truncates — at the 641px side-by-side floor the labels measure 54/60/117px inside a 227px button — so no `wrap=` is passed; it is recorded because the four buttons no longer share one wrapping rule, and an overflowing label would now ellipsize on three of them and grow the row on the fourth
- Full-width buttons use `width="stretch"` — Streamlit 1.58's replacement for the deprecated `use_container_width`; a source-level test in `test_streamlit_app.py` guards against reintroducing the old arg. There are **four** of them (translate, download, translate_doc, download_doc), not six
- The two swap buttons are pinned to `width=40` inside `col.container(horizontal=True, horizontal_alignment="center")` and are **deliberately not stretched**. Every `st.columns` child picks up `min-width: calc(100% - 1.5rem)` below the 640px breakpoint *regardless of its weight*, so the 1-unit swap column becomes a full row — and a `type="tertiary"` button paints no background or border, so a stretched one became an **invisible full-row tap target** between the two pickers: measured 425×40 at a 500px viewport, clickable edge to edge, one stray tap from wiping the Text tab's output. A fixed 40 clamps to the parent, so the desktop rendering is unchanged and only the hit area moves. It does **not** rescue the 640–800px band, where the column shrinks toward the 16px icon and 40 clamps with it
- The four action buttons carry icons (`:material/translate:` on both produce actions, `:material/download:` on both save actions) — previously they were distinguished only by fill colour, which reads as two peers when Translate is the expensive state-changing operation and Download is a passive export that is disabled most of the time
- The Text tab reserves its output panel with `output_placeholder.skeleton(height=PANEL_HEIGHT)` at click time, rather than announcing the translation with a bare `st.spinner` at the script cursor — that cursor sits below both the panels and the controls row, the off-the-fold trap `ensure_model` and `doc_status_slot` already document. `warning_slot` was rejected because it sits *above* the panels and would shove the row down for the duration. The skeleton reflows nothing and clears the previous translation, which used to sit there looking current. There is **no `st.spinner` alongside it** — that would be a second indicator for one operation, at the very position the reasoning rules out
- **Every exit path of the Text translate block ends in `st.rerun()`**, so the panel is always repainted from `translate_output` rather than patched in place. That is what lets the *empty state* come back as its `text_area`, which cannot be re-emitted in the same run (the widget id would collide) — an earlier version painted a blank `st.code` instead and left a featureless grey rectangle after a first-run failure
- `translate_notice` (`("warning" | "error", text)`, or `""`) carries the message across that rerun, drained and cleared immediately under `warning_slot`. Without it the rerun that repaints the output would also discard the explanation for it. The three *pre-stream* checks — empty input, same language, over token budget — do **not** rerun and still write to `warning_slot` directly
- On empty output the block clears `translate_output` and `download_name`, because **state has to agree with the message**. An earlier version restored the previous translation to clear the skeleton, which put a downloadable translation of *different input* directly beneath "the model returned an empty translation" — verified by reproduction, download button live, name still `translation-French.txt`
- A mid-stream failure now **keeps the partial**, with a `translation-<Target>.txt` name and a "failed after partial output" error, matching what the Document tab already did. Before, the streamed text was visible but unreachable and vanished on the next rerun

### Loading the model and running inference

- Translation model loads **lazily**: `@st.cache_resource def load_model()` wraps `mlx_lm.load`, and `ensure_model(warning_container)` calls it from inside the translate handlers — after the free empty-input and same-language checks, before the tokenizer is needed — rendering **both** the spinner and any failure into the container it is handed -- `warning_slot` on the Text tab, **`doc_status_slot`** on the Document tab -- and returning `None`. The spinner has to go in the slot: inside a translate handler the script cursor is below the panels and the controls row, so a bare `st.spinner` put the only sign of activity below the fold while the error appeared at the top. `@st.cache_resource` is process-global (shared across every session and user, not per-session), so the load happens once per server process, and it does **not** memoize exceptions — a failed load leaves the button live and a later click retries. Loading eagerly at page load put the whole UI behind ~3.6 GB of weights: no tabs, no language pickers, nothing to type into while it read. Consequently the translate buttons are **not** gated on a `model_loaded` flag — there is no cheap way to know the model loads without loading it, so a broken install surfaces on click, next to the action that caused it
- Both tab bodies still execute on every rerun. `st.tabs(..., on_change="rerun")` + `.open` would make them lazy; considered and skipped. The heavy work is already behind button guards, so what it saves is a per-rerun re-encode of the Document tab's output — **not** a doubled payload, as an earlier version of this bullet claimed. `download_button` does **not** ship its `data`: the `DownloadButton` proto has no `data` field at all, and `marshall_file` registers the bytes with the media-file manager and sets only `url`, so the browser receives a link. The real cost is server-side: a UTF-8 encode plus hash of the whole output for the button, and an unchanged `st.code` sent as a ref-hash. Measured on whole-app reruns with populated state — 16.7 ms empty, 17.9 ms at 180 KB, 20.0 ms at 1 MB, so roughly 3 ms per MB across both elements. Against that, `on_change="rerun"` costs a server round-trip per tab switch and risks Streamlit purging the unrendered tab's widget state, which the `setdefault` block above the tabs would silently re-seed to English/French. If revisited, gate only the output rendering, not the whole tab body
- `tokenize_prompt` applies the chat template with `tokenize=True` and returns the prompt token ids — its `len()` gates against `MAX_INPUT_TOKENS`, and the same ids are passed to `stream_translate` so the prompt is tokenized exactly once per translation
- `stream_translate` takes pre-tokenized prompt ids, calls `mlx_lm.stream_generate` with `sampler=make_sampler(temp=)`, and yields the cleaned running result after each chunk
- `clean_model_output` strips whitespace and the `<|END_RESPONSE|>` token leaked by the model
- UI tests use `streamlit.testing.v1.AppTest`; mocks target `mlx_lm` because AppTest runs scripts via `exec()`; download buttons have no named accessor, so `at.get("download_button")` returns both (`[0]` Text tab, `[1]` Document tab). Since Streamlit 1.63 (#16711) AppTest raises `AppTestError` on `set_value`/`click`/`upload`/`clear` against a **disabled** widget — `at.button("translate_doc").click()` before an upload, or `set_value` on either tab's disabled empty-state output `text_area` — where 1.61 silently reran. No test does either; a Document-tab test must upload first (`test_document_ocr_failure_shows_the_error_not_the_blank_guard` is the pattern), and the output panels are read-only (assert on `.value`)

### Document parsing and OCR

- Document functions (`load_document_markdown`, `chunk_text`, `translate_document`, plus the `heading_level` / `heading_line` / `token_overhead` / `count_tokens` / `sentence_units` / `split_oversized` / `repack_blocks` helpers) are pure functions with a deferred `liteparse` import. Document support has **no** availability gate and no install hint: `liteparse` is a required dependency, one ~12 MB abi3 wheel with zero transitive deps. The project previously used Docling behind an optional `docs` extra — that extra existed only to keep Docling's ~278 packages and PyTorch out of a text-only install, and it was removed along with Docling
- `load_document_markdown` runs LiteParse with `output_format="markdown"` and `quiet=True` (its `[liteparse] extract/ocr/project/markdown/total: …ms` timing lines would otherwise print to the server's **stderr** — measured at the fd level on 2.11.1 and 2.14.4, fd 1 stays empty either way; `quiet` does **not** silence the `[ocr] failed for page N: …` lines, which go to stderr regardless). It takes bytes only, and **sniffs `%PDF` itself** (`is_pdf`) to set `ocr_enabled` — the one format decision made in-app rather than left to LiteParse. The Document tab's blank guard asks the same helper, because the policy has a visible consequence: a scanned PDF has no text layer, so under `ocr_enabled=False` it parses to the empty fence and used to be reported as "No translatable text found" — not blank, and the wording sent people looking for a fault in the file. It now says the PDF has no text layer and that OCR runs only on image uploads (export the pages as PNG/JPEG); the blank-image case keeps the original wording, since there OCR did run and found nothing. A read failure (LiteParse raising) has its own `except` and label, "Could not read the document: …", because it used to share the translation loop's `except` and announced an unreadable image as "Translation failed: OCR failed …" about a translation never attempted. The policy is *OCR only where it is the sole extraction path*, and both directions were bugs found in review:
  - `ocr_enabled=False` everywhere (the original) made every image type return an empty ```` ```text``` ```` fence. An image has no text layer, so OCR is not an enhancement on top of one — it is the only way to read it
  - `ocr_enabled` left at LiteParse's auto default (the first fix) made PDFs reach for OCR on sparse pages, which **downloads ~15 MB of Tesseract training data from GitHub** into `~/Library/Application Support/tesseract-rs/tessdata/` on first use — unacceptable in an app whose README promises nothing leaves the machine, and a hard `ParseError` when offline. Verified: with an empty cache a born-digital PDF fetched 15 MB; PDFs now parse in ~0.04 s with zero network
- `ocr_failure_fatal` is left at LiteParse's default (`True`). It used to be passed as `False` "so an OCR attempt that cannot fetch its data never kills a parse whose text layer was readable all along" — a rationale from before the `%PDF` sniff, when PDFs could still reach for OCR. Now only images run OCR, and an image has no text layer to fall back to, so `False` could only turn an offline or uncached-traineddata failure into the empty ```` ```text``` ```` fence, which the tab reported as "No translatable text found". Verified on 2.14.4 with an empty `HOME` and a dead proxy: `False` returned the fence (liteparse's own stderr line says it is "continuing with partial (native-text) results"), the default raised `ParseError: OCR failed: … error sending request for url (https://github.com/tesseract-ocr/tessdata_best/raw/main/eng.traineddata)`, which the Document tab's `except Exception` reports as "Translation failed: …" and `st.cache_data` does not memoize, so a retry once online works. `is_blank_markdown` still collapses the fence a *successful* OCR of a blank image returns, so the guard keeps firing for a blank image — and for a scanned PDF, which arrives as the same fence under the offline policy and is now named as such rather than called blank (see the `is_pdf` bullet above); the empty fence is not blank and used to be sent to the model as a prompt
- **Images need a one-time ~12-15 MB traineddata download per OCR language**; nothing is bundled. The traineddata lives in liteparse's own cache dir (`~/Library/Application Support/tesseract-rs/tessdata/`), *not* in the wheel — an earlier reading of this repo claimed it was embedded in the `.so`, which was wrong (the `unicharset`/`lstm-punc-dawg` strings in the binary are Tesseract's symbol names)
- The upload filename is **untrusted input** and reaches two places that need it sanitised, neither of which was true when the name was the fixed literal `translation.md`. `escape_markdown` backslash-escapes CommonMark punctuation before the name reaches `st.caption`, which renders GFM — `*draft*.pdf` rendered as italic *draft.pdf*, and `[r](https://…).pdf` as a live link, in the caption whose whole job is stating the filename accurately. `safe_download_stem` strips quotes, slashes and control characters before the name reaches `Content-Disposition`, which Streamlit builds as `f'filename="{filename}"'` with **no quoting**, so `re"port.pdf` saved as `re`. Non-ASCII is deliberately **kept**, but note which branch it takes — Streamlit selects on `filename.encode("latin1")`, **not** on ASCII. `Bokmål` encodes to latin1 and goes down the *quoted* branch as a raw `0xE5` byte (RFC 6266 reads an unencoded filename as ISO-8859-1); only genuinely non-latin1 names like 報告 reach `filename*=utf-8''{quote(...)}`. Both are handled, and the escape class is **all ASCII punctuation** rather than a hand-picked list, because `st.caption` also renders LaTeX (`$…$`), emoji shortcodes (`:tada:`) and HTML entities
- The Document tab clears its provenance caption (`doc_meta_slot.empty()`) the moment Translate is committed, and `_restore_doc_meta()` puts it back on **every** path where nothing changed: same language, no translatable text, an unreadable document, total failure, **and a failed model load** — that last one is an `else` on the `ensure_model` chain, and was the one exit that originally fell through, leaving the previous translation on screen unlabelled. Left up, it spent the whole model-load-plus-parse window — minutes on a cold cache — asserting a pair the controls no longer matched while new text streamed in underneath
- `OCR_LANGUAGES` maps the Document tab's **source** language to a Tesseract code, threaded through `load_document_markdown(file_bytes, source_lang)` and into `cached_document_chunks`' cache key (it changes the parsed text, so it has to be part of the key). Without it OCR ran as English on every scan and returned confident-looking Latin garbage: `Быстрая коричневая лиса прыгает через собаку.` came back as `BbicTpasi Mca npbiraeT cobaky.` with two words silently dropped, and Japanese as `2.` — all non-empty, so all past the "no translatable text" guard. With the right code both are exact. Only languages Tesseract publishes data for are listed; Hausa, Igbo, Malagasy, Shona, Wolof, Xhosa and Zulu have none and fall back to `eng` rather than requesting a file that does not exist
### Chunking

- LiteParse ships **no chunker**, so `chunk_text` is where a document becomes translatable pieces: it splits on blank lines, packs blocks greedily under the budget, splits over-budget blocks on sentence boundaries (Latin *and* CJK enders) and finally on hard token windows, and prepends the enclosing markdown heading trail — context that matters because each chunk is translated as an independent prompt
- `chunk_text` accounting has three traps, all covered by tests: the tokenizer prepends a BOS to **every** `encode` call (so `count_tokens` subtracts `token_overhead`, or an N-block chunk is charged N BOS tokens), joining blocks costs a `\n\n` separator each, and BPE still merges across block boundaries — so `flush()` measures the assembled chunk. Drift measures ~1 token per block, far inside the `MAX_CHUNK_TOKENS`/`MAX_INPUT_TOKENS` headroom. `SpecialTokenTokenizer` in the tests simulates the BOS and separator costs; the plain `FakeTokenizer` cannot catch this class of bug, and `DriftingTokenizer` (which spends an extra token per block join) is the only one that reproduces the overflow itself
- When the measured chunk *is* over, `flush()` calls `repack_blocks`, which re-packs whole blocks against measured sizes. It must not call `split_oversized` on the assembled body: that splits at every sentence and dissolves the `\n\n` between blocks, so a 7,330-token document at `MAX_CHUNK_TOKENS` came out as **277 single-sentence chunks instead of 3** — one translation call each, every one stripped of its neighbours. Drift overflow fires on essentially every *full* chunk, so this was the common path, not an edge case. `test_chunk_text_does_not_shatter_a_full_chunk_when_the_estimate_drifts` asserts the chunk **count**; the budget tests only bound chunk size, and hundreds of tiny chunks satisfy an upper bound perfectly
- `pack_by_estimate` is the shared greedy grouper: one token count per unit, plus a `join_cost` charged per join, and the caller measures each finished group once. Measuring every growing candidate instead is **quadratic** — a single 16.8k-token block took 3.85 s and a CJK one 36 s, against 0.16 s / 0.49 s now. `join_cost` is not optional for block callers: omitting the `\n\n` separator let 985 blocks estimated at 5,792 tokens measure 7,760, and that overflow fell through to the fallback that strips heading context
- `repack_blocks` takes the **full trail**, not the caller's deduplicated context, and re-derives context per piece via `leading_headings`. Two ways a piece ends up unlabelled if this is skipped: a piece cut from the middle contains none of the headings the first piece opened with, and the *first* chunk of a document opens before any heading has reached `trail`, so its headings exist only as its own blocks. Its fallback path assembles each sub-group with context too — falling straight through to `split_oversized` is what dropped the labels
- `leading_headings` returns only the headings a chunk **opens** with. De-duplicating context against *every* block in the chunk looks tidier but is wrong: when the next section repeats a heading text inside the same chunk, it strips that heading from the body that actually belongs to it — 102 paragraphs reaching the model labelled only with the document title
- `split_oversized` re-packs sentence units up to the budget rather than emitting one piece per sentence, and strips the BOS prefix before slicing token windows, or `decode` would write the special token back into the translated text
- `hard_windows` pulls a window boundary back (up to `_MAX_CHAR_TOKENS`, four bytes of UTF-8) until the window decodes without U+FFFD. A byte-fallback tokenizer spends several tokens on one character in Thai, Lao, Khmer, Burmese, Amharic and rarer CJK — all in `LANGUAGES` — so a fixed stride cut characters in half, and the halves decoded to U+FFFD with the character **lost outright** before reaching the model. `ByteFallbackTokenizer` in the tests is the only fixture that can see this: it encodes non-ASCII to real UTF-8 bytes and decodes with `errors="replace"`, where the whitespace fakes round-trip perfectly and cannot
- `sentence_units` splits on `(?<=[.!?])\s+|(?<=[。！？])\s*` — the two branches need different whitespace rules. Latin prose puts a space after the ender, and *requiring* one is what keeps `3.14` intact; CJK writes 。 flush against the next sentence, so demanding whitespace there meant real CJK never split at all and fell through to mid-clause hard token windows. Units carry their own trailing gap so concatenating them reproduces the source exactly — rejoining on a space would insert one CJK never had
- When the heading trail would leave less than a quarter of `max_tokens` to work with, `chunk_text` **drops the context** instead of clamping the budget to 1. Clamping shredded the document: a 7,002-token trail against the 7,000 budget turned 13,121 tokens of markdown into 12,082 chunks over 292 s, then 12k `stream_translate` calls. Now 4 chunks in 0.12 s. A chunk carrying less context still translates; a chunk of one token does not. `chunk_text` and `hard_windows` both clamp `max_tokens` to at least 1 — a zero budget made `hard_windows`' boundary pull-back loop spin forever, since a zero-width window never advances past its own start
- Blocks inside a ```` ``` ```` fence never update the heading trail. `_BLANK_LINE_RE` splits a fence at its internal blank line, so a `# clean up the build tree` comment inside one arrived as its own block, read as an H1, and evicted the real heading — every chunk below it was then labelled with a line of shell. The fence flag is toggled by the parity of the marker count per block, so it has to be carried across blocks and cleared again on close
- The heading trail is snapshotted when a chunk *opens* (`pending`), not read at flush time — `trail` advances as blocks are consumed, so flushing against it labels a chunk with the heading of the section that comes *after* it. `trail` stores `heading_line(block)`, **not** the block: blocks split on blank lines, so a heading followed immediately by its opening body line is one block, and storing it whole prepended that body text to every later chunk and charged its tokens against the budget the trail reserves
### Supported formats

- `DOCUMENT_TYPES` is PDF + images: liteparse bundles PDFium as `libpdfium.dylib` inside the package (6.5 MB, loaded from there at first use) and links Tesseract into `_liteparse.abi3.so` (20 MB), so neither needs a binary on `PATH` (Tesseract's *training data* is still fetched on first OCR — see above). The tiers below were **probed against liteparse 2.11.1 and re-probed against 2.14.4 with real generated files** — identical tiers, identical error strings, byte-identical markdown for every native file — not read off its README, whose "Supported Formats" section stops at "Images (`.png`, `.jpg`, `.tiff`, etc.)" and "And more!":
  - **Native, nothing on `PATH`** — PDF, PNG, JPEG, TIFF, WebP, and also **BMP and GIF**. Those last two are genuinely supported and deliberately *not* offered; nobody translates a GIF
  - **Needs LibreOffice on `PATH`** — `.docx`, `.pptx`, `.xlsx`, `.odt`, `.ods`, `.odp`, `.rtf`. They fail with `conversion error: LibreOffice is not installed`, a *conversion* error rather than an unsupported one, because every non-PDF input is converted to PDF before parsing
  - **Rejected outright** (`unsupported file format`) — `.html`, `.epub`, `.heic`/`.heif`, `.ico`, `.tga`, `.jp2`, `.ppm`/`.pgm`, and the entire plain-text family: `.txt`, `.md`, `.csv`, `.json`. **Plain text being unreadable is not a bug**: everything normalizes to PDF first and no code path simply returns bytes as text, so `.txt` has nothing to convert *from*. The `Cannot screenshot text-based format (.<ext>). Convert to PDF first.` string in the native module is the same rule surfacing elsewhere
- liteparse **sniffs content, never the extension** — `parse(bytes)` is handed no filename, so its errors report what the magic bytes said: a greyscale P5 file saved as `.ppm` comes back as `.pgm` (a colour P6 one reports `.ppm`), a `.tga` as `.cur`, and `.md`/`.csv`/`.json` all as `.txt`. `load_document_markdown`'s own `%PDF` sniff is therefore the same question asked the same way, not a workaround
- **Both TIFF spellings are listed.** `DOCUMENT_TYPES` reaches the browser as the file picker's type filter, so `tiff` alone left a `scan.tif` **greyed out and unselectable** with nothing on screen to explain it, though the parser reads either. **HEIC is the trap in the other direction**: it is the iPhone camera default and so the tempting addition, and it even appears in the native module's sniffer vocabulary — but it is still rejected at parse time, so listing it would only move the failure from the picker into `load_document_markdown`. A real fix would be pre-conversion (`sips` ships on every Mac), not a list edit. `test_document_types_are_liteparse_native` pins both halves: both TIFF spellings present, and `heic` absent alongside `docx`/`pptx`/`xlsx`/`html`
### Document tab

- `cached_document_chunks` (defined after `load_model`, decorated `@st.cache_data(max_entries=8, show_spinner=False)`) wraps `load_document_markdown` + `chunk_text` so re-translating the same upload skips the parse+chunk; the file bytes are the whole cache key. It fetches the tokenizer from `load_model()` internally rather than taking it as an arg (the tokenizer is unhashable and would defeat `@st.cache_data`'s key hashing). The Document tab calls this wrapper, not the pure functions directly; the pure functions stay for unit tests
- Because that wrapper bundles the parse with the chunking, a blank image or scanned PDF still pays the model load before it reaches the no-text guard, and an unreadable image pays it before its `ParseError` is reported — `load_document_markdown` needs no tokenizer, but `chunk_text` does. Splitting it into a markdown cache (no tokenizer) and a chunk cache would let that rejection come first; considered and not done, because `@st.cache_resource` is process-global, so it only bites when a blank upload is the **first** model-requiring action in a fresh process. Revisit only if that ordering starts mattering — the split touches this bullet, `test_document_tab_calls_cache_wrapper`, and both `cached_document_chunks` unit tests
- `translate_document` reuses `tokenize_prompt` + `stream_translate` per chunk and yields `(chunk_index, cumulative_text)` on every token; chunks join with `\n\n`
- `MAX_CHUNK_TOKENS` (7000) sits below `MAX_INPUT_TOKENS` to leave room for the per-chunk prompt wrapper (instruction + chat template); `translate_document` still re-checks each chunk and emits a `[Section skipped]` marker for any prompt over `MAX_INPUT_TOKENS`
- The Document tab uses a plain `if st.button():` block (no `_do_translate` flag, no `st.rerun()`): output streams into an `st.code` placeholder, its `doc_source_lang`/`doc_target_lang` selectboxes use distinct keys to avoid widget-id collisions, and the `download_doc` button is rendered last so it picks up `st.session_state.doc_output`
- The Document tab re-renders its `st.code` output only on chunk boundaries — re-sending the whole accumulating document every token would be O(n²); a mid-document failure still saves the partial result to `st.session_state.doc_output`. The **status label lives inside that same guard**, and did not always: `translate_document` yields per *token* while both the label and the output change only when the chunk index does, so the unguarded version emitted two identical deltas per token — 1.15 s of server work per 15k tokens against 1.5 ms guarded
- Document-tab activity is reported by `doc_status_slot.status(...)`, **not** a progress bar. Two reasons, both defects in the pair it replaced. A fraction is the wrong shape: chunks complete, so the only honest value is `idx / len(chunks)`, which reads 0% for the whole of the first chunk and therefore for the entire run of a single-chunk document. And `StatusContainer.__exit__` settles the state itself — `complete` on a clean exit, `error` when an exception propagates — where the old `st.progress` + `st.empty()` caption cleared only on the success path, stranding a half-filled bar and a live "Translating section k of n" underneath the error message. It is `type="compact"` because its body is empty — `render_output` targets an `st.empty()` declared *outside* the block, so the default bordered expander would wrap nothing to expand
- The Document tab has an **empty state**: an `else` on `if st.session_state.doc_output` paints a disabled `text_area` at `PANEL_HEIGHT`. Once Download moved up beside Translate the tab ended at two disabled buttons with nothing after them, reading as a converter that only ever hands back a file; the panel also reserves the footprint `render_output` will fill, so the first chunk lands in place instead of shoving 450px of page into existence. Its label differs from the Text tab's (`Translated document`) to keep the two auto-generated element ids apart. **Three `text_area`s exist at rest**, not two — several UI tests count them
- The OCR notice under the uploader is **`st.info`, not `st.caption`**, and the reason was originally contrast; the reason that survives the theme change is semantics. `st.caption` renders as `opacity: 0.6` on inherited body text — `color: inherit` plus `opacity`, never reading the `grayTextColor` key, which exists and holds the same value — so under the stock theme it landed `#31333f` on `#ffffff` at **3.69:1** in light, under AA, and a markdown colour directive could not rescue it because it is multiplied by the same opacity and comes out worse. An earlier version of this bullet concluded that **nothing in `config.toml` could reach it** — true of a colour directive, wrong about the ink: the composite is `textColor` at 60% over `backgroundColor`, and the Reading Room palette's darker `#0e0d0b` ink lifts the caption to `#6c6a66`, **4.96:1 light**, and `#949088`, **5.78:1 dark** (stock dark was 6.96), with `test_caption_readable_in_both_modes` holding both at ≥ 4.5. `st.info` paints `blueTextColor` on `blueBackgroundColor`: stock's 6.68:1 light / 4.90:1 dark, now the theme's explicit slate at **6.36:1 light and 7.12:1 dark** (box 1.13:1 against the paper, 1.40:1 against the dark page) — designed rather than inherited because the notice is persistent, and on a hue (~211) chosen to sit far from the accent's 166 so it never reads as the accent. What keeps it an `st.info` now that a caption would also clear AA: the line is an instruction with a silent-failure mode and a network side effect, which is `design.md`'s info row, not its caption row. The Document tab's *provenance* caption stays a caption — it is metadata, and a second persistent blue box in the same column would be worse — and the 3.69:1 gap it carried as a **known, accepted** miss is closed by the same ink, not by a change to the element
- `doc_status_slot` is a third container, declared above `doc_output_placeholder` alongside `doc_warning_slot` and carrying **both** the "Reading document..." spinner and the translating status. Warnings and errors go to `doc_warning_slot`, activity to `doc_status_slot`. `ensure_model` is the one call that writes **both** kinds into the status slot, because it owns a spinner and an error and cannot split them; that is the exception, not a second rule. `ensure_model` is passed **`doc_status_slot`**, not the warning slot: its spinner is activity, and it is the longest-lived indicator on the tab. The placement is the `ensure_model` rule applied to the Document tab: once the first chunk lands the output panel is `PANEL_HEIGHT` tall, so anything created at the script cursor below it spends the whole run below the fold
- The file uploader is keyed `doc_upload` with `on_change=clear_doc_output`, because `st.session_state.doc_output` outlives the upload it came from. Without it a new file rendered — and offered for download as `translation.md` — the *previous* file's translation, with nothing tying the output to the filename above it; it also defeated the "No translatable text found" guard, which fired directly above the last document's intact output. The callback also runs when the file is cleared, which is the same invalidation
- `MAX_UPLOAD_MB` (50) caps the uploader widget alone, and is a **frontend hint, not a server guarantee** — `starlette_routes.py` still rejects against `server.maxUploadSize` (200 MB), so a POST straight to `/_stcore/upload_file` is unaffected. Acceptable for a localhost single-user app, but it is a browser-path mitigation and the comment says so. Streamlit's server default is 200 MB, and a file that size goes straight into in-process PDFium/Tesseract with ~3.6 GB of weights already resident; the browser now rejects oversized uploads before a byte reaches the parser. It is a widget parameter (`max_upload_size`), so it needs no `[server]` section in `config.toml`
- Default download names live in `DEFAULT_TEXT_DOWNLOAD` / `DEFAULT_DOC_DOWNLOAD`. They used to be inlined at three and two reset paths respectively, so changing one left the others behind with nothing failing; a source-level test now pins each literal to exactly one occurrence
- Both `st.download_button` calls pass `on_click="ignore"`. The default is `"rerun"`, and a download changes no server state — so every click was re-executing both tab bodies, re-rendering the Document tab's output and re-encoding it for the button, to produce a byte-identical page
### Model and theme

- The app uses one model: `mlx-community/tiny-aya-global-8bit-mlx` (CC-BY-NC, non-commercial only)
- `.streamlit/config.toml` is the project's **own theme, "Reading Room"** — a warm-neutral ink-and-paper palette with one verdigris accent, dark-first, both modes stated in full. It replaced a restated copy of Streamlit's stock theme on 2026-09-11, which had itself replaced a hand-built Nord theme; both predecessors are in git history. **The comment block at the top of the file is the full record** — every value with its measured ratio, the derived states (hover, focus ring, caption, placeholders, borders, skeleton, status tints) emulated from the 1.63.0 bundle's own colour functions, and the alternatives rejected on the way — so cite it rather than duplicate it here; this section carries what an editor of *this* repo needs to not break it. What stating both modes earns is narrower than it looks: once a *custom* theme exists at all, Streamlit drops its built-in presets from the menu (`keepPresetThemes:!1`), and the System/Light/Dark radio in the ⋮ menu is rendered only when more than one theme is available (`if(t.length<=1)return[]`) — a lone `[theme]` yields a single internal `Custom Theme` and the radio disappears entirely, rather than showing a locked entry as an earlier version of this bullet claimed. Any key in **either** `[theme.light]` or `[theme.dark]` is enough to get the three-entry list (Custom Theme Light / Dark / Auto — the check reads `let t=bn(e.light),n=bn(e.dark),r=[];if(t||n)` in 1.63.0's `utils.Bid3C9ZE.js` — grep for `.light),n=` since the helper name moves; 1.61.1 had the same shape as `Iu`, and the missing side is derived from `[theme]` on the stock base), so stating both is this project's choice to spell out both palettes, not a Streamlit requirement — and here it is also how the two palettes stay designed rather than derived. A repo with **no** config at all still gets the full System/Light/Dark switch, so the file is not what earns the toggle — an earlier version of this bullet claimed it was, which is also wrong. While the file restated stock, deleting it would have been visually identical; it no longer would be
- **22 keys, all valid in Streamlit 1.63.0**: two type keys under `[theme]` (`headingFont = "serif"`, `codeFont = "sans-serif"`), twelve colours under `[theme.light]` and eight under `[theme.dark]`. Palette, as primary / background / secondaryBackground / text / link: light `#287160` / `#f8f5ef` / `#ebe5da` / `#0e0d0b` / `#287160`, dark `#33826f` / `#161412` / `#2f2b27` / `#e8e2d6` / `#5bae9b`. Both modes pin `codeBackgroundColor` (next bullet) and restate `st.info`'s blue pair as a cool slate — designed rather than inherited because the OCR notice is persistent, and on a hue far from the accent's so it never reads as one. Light alone also restates the yellow and red pairs, because stock's alert text was tuned for `#ffffff` and drops under AA on paper; dark leaves both at stock. Note the attribution the bundle actually makes: `st.warning` paints `yellowTextColor` on `yellowBackgroundColor`, **not** orange — nothing in the app paints an orange key, so none is set and none should be "fixed" later. Everything else — radii, weights, `linkUnderline`, `showWidgetBorder`, `codeTextColor`, `borderColor`, `codeFontSize`, `baseFontSize` — is **deliberately absent** and falls back to Streamlit's defaults: 16px base, 0.5rem radius, underlined links, and **no outlines on any widget** — the text areas, both selectboxes and the file uploader are separated from the page by fill alone. Two of those absences are load-bearing rather than lazy. `showWidgetBorder` is not a lever for stronger panel edges: `st.code`'s `<pre>` paints `codeBackgroundColor` and `bodyText` with **no border property at all**, while the `text_area`'s border is `widgetBorderColor`, so turning the flag on would outline the input and not the output beside it. `codeTextColor` reaches only inline code (wherever markdown renders it, alerts included) and `st.help`'s type labels — never the output panel, which paints `bodyText`. There is **no custom CSS** anywhere; every colour on screen is a theme key or a value Streamlit derives from one (`borderColor` is `fadedText10`, which despite its name is `textColor` at 20% alpha; disabled labels are `fadedText40`; the output skeleton and selectbox highlight are `darkenedBgMix15`) — the derived hexes and their ratios live in `config.toml`, not here. The project previously shipped a hand-built Nord theme with a custom Inter/JetBrains-Mono type scale, 4px radii, `showWidgetBorder = true` and Aurora status colors, then a verbatim copy of stock; both are gone. `.gitignore` tracks `config.toml` but ignores the rest of `.streamlit/` (e.g. `secrets.toml`)
- `codeBackgroundColor` is pinned to `secondaryBackgroundColor` in both modes — under stock it was the **one deliberate departure**, and it survives the new palette unchanged, now guarded by `test_code_background_matches_secondary_background` (which compares normalised colours, so a case-only respelling cannot fail it). It is not cosmetic pedantry. The reason is **spatial, not temporal** — it used to be temporal, and that reason is now dead. The old one: the Text tab streamed into `st.code` then swapped in a settled disabled `text_area`, so the panel changed shade the moment a translation finished. **That swap no longer exists** (settled output renders through `st.code` too), so do not go looking for it. What survives is stronger: the input `text_area` (painted `secondaryBackgroundColor`) and the output `st.code` (painted `codeBackgroundColor`) sit **side by side in one row**. Unset, `codeBackgroundColor` falls back to Streamlit's `bgMix`, a 50/50 blend of the two backgrounds — which would make two adjacent panels of one workspace two permanently different shades across a 16px gutter. One trap when emulating any bundle-derived colour: the bundle rounds with JS `toFixed()`, which takes `.5` ties **up**, where Python's `round()` is banker's and lands one 8-bit step low on every tie — the `bgMix` figures in `config.toml` were corrected for exactly that. `codeFont = "sans-serif"` is the typographic half of the same pin (see the type bullet below)
- **"Stock" in `config.toml` and in this file means Streamlit's built-in palette** — the values the file restated until 2026-09-11 and the reference every before/after ratio is measured against: light `#ff4b4b`/`#ffffff`/`#f0f2f6`/`#31333f`/`#0054a3`, dark `#ff4b4b`/`#0e1117`/`#262730`/`#fafafa`/`#3d9df3` (primary/background/secondaryBackground/text/link). They were unchanged from 1.61.1 through 1.63.0, re-derived 2026-09-10 by diffing the 1.61.1 wheel's bundle against the installed one — extracted from the installed frontend bundle, **not** recalled from memory, and worth re-deriving the same way if they ever need checking. In 1.63.0 that bundle is `static/static/js/utils.Bid3C9ZE.js`, where the colour scale is `z`, the light override object is `St` (`bgColor:z.white`) and dark is `Et` (`bgColor:z.gray100`); the hash in every bundle filename and every minified name moves each release (1.61.1 was `utils.KTqwHXHU.js` / `wl` / `kl`), so locate the file by grepping for `#ff4b4b` and the objects by `bgColor:`. The one non-byte-exact detail is that the bundle spells gray85 `#31333F` with a capital F. `linkColor` is the one non-obvious entry: `config.py` documents it as defaulting to the resolved `blueTextColor` — blue90 `#0054a3` light, blue60 `#3d9df3` dark — **not** the `secondary` blue70 `#1c83e1`, which is a different token and 3.90:1 on white. The **derived** states live in `getColors.CymiOtHO.js` — `bgMix`, and the functions behind hover, focus, caption, placeholder, border and skeleton colours: `darken`/`lighten` are HSL with integer-rounded `hsla()` output, `transparentize` is a straight alpha — which is how every derived figure in `config.toml` was emulated without a browser; they match what one paints to within one 8-bit step (the theme keys themselves land byte-exact; the composited hairlines can sit one step off). The same reading of the bundle pins the mechanics the accent depends on: the primary button is `primaryColor` fill with a **fixed white** label, hover and `:focus-visible` are darken-15%, the focus ring is the primary at 50% alpha; the active tab label is `primaryColor` as 14px/400 text on `backgroundColor` plus a 2px indicator, inactive tabs are `bodyText`; the secondary button is `lightenedBg05` fill with a `borderColor` stroke, and disabled is a transparent fill, the `borderColor` hairline and a `fadedText40` label
- **The accent is text twice under WCAG SC 1.4.3, and no single colour can pass both on a dark page.** Streamlit paints the primary button's label white (fixed, not themeable) and paints the active tab label in `primaryColor` as 14px/400 text on `backgroundColor` (`[data-testid="stTab"][aria-selected="true"]`). White-on-primary ≥ 4.5 needs L(primary) ≤ 0.1833; primary-on-page ≥ 4.5 on `#161412` needs L ≥ 0.2072; both hold together only on a page at or below ~`#050505`. So a side is chosen, and it is the **button**: dark white-on-`#33826f` is **4.60:1** (the Translate label, passes), and `#33826f` on the page is **3.99:1 — the theme's one knowing AA text failure**, the active tab label, which still clears the 3:1 non-text floor for its 2px indicator and is named three times over (indicator, position, the content already showing under it). Light needs no trade and has **zero AA text failures** (5.80 button, 5.33 tab). Under stock the red was 3.30:1 under the white label in **both** modes and 3.30 as the light tab label — two knowing failures — and the button test had been lowered from 4.5 to 3.0 to admit it (an earlier bullet justified the 3 as SC 1.4.11, wrong twice over: 1.4.11 measures a component against the *adjacent* background, not its own label, and text inside a control is carved back out to 1.4.3). It is now **`test_primary_button_label_readable_in_both_modes`** with the **4.5 floor restored**. The admissible band is a **knife-edge**, because the same colour is the 1px focus border on the panels (3.05:1 dark, SC 1.4.11) and the label and the border pull L(primary) in opposite directions: ±1 on every RGB channel of the dark primary keeps both, **+2 drops the label to 4.48, −2 drops the focus border to 2.97**. Re-run the helpers (`_relative_luminance` / `_contrast_ratio` / `_composite` in `test_streamlit_app.py`) before changing a digit of `primaryColor`, `backgroundColor` or `secondaryBackgroundColor`; the ACCENT block in `config.toml` carries every measured pair and the alternatives rejected. Seven theme tests make it durable: the label test above; `test_primary_focus_border_clears_non_text_floor` (primary on `secondaryBackgroundColor` ≥ 3.0); `test_active_tab_label_does_not_regress` (primary on `backgroundColor` ≥ 3.5 — a regression guard, not a standard being met, and named so it cannot advertise one); `test_caption_readable_in_both_modes` (the 0.6 composite ≥ 4.5); `test_code_background_matches_secondary_background`; `test_theme_fonts_are_bundled_not_fetched` (walks every nested table and `base`); and `test_usage_stats_are_off`. The helpers normalise through `_hex6`, so a `#rgb` short form or an upper-case respelling — both valid to Streamlit — cannot crash a ratio test or fail a guard on spelling alone. What the button side costs is stated, with numbers, in `config.toml`: the selected tab is dimmer than the inactive ones and carries on chroma and the indicator; the hover fill sinks toward the dark page rather than lighting (move the pointer off before a screenshot); the 50%-alpha focus ring fails the 3:1 non-text floor in both modes exactly as stock's did, and the 1px primary border is the cue that does clear it on the text areas and selectboxes; on the primary button itself `:focus-visible` shows only as the fill sinking, which is Streamlit's primary-button styling under any theme, not a cost of this accent
- `test_link_text_readable_in_both_modes` still demands a genuine 4.5:1 — its floor was not touched, only its comment, to note why the dark link is not the primary — and it is why dark `linkColor` is **split from the primary**: `#5bae9b` (the accent's text weight, same hue) is 6.98:1 on the page, where the button-side `#33826f` would sit at 3.99 and fail the test outright. Light keeps `linkColor == primaryColor`. The app paints no links today; the key exists to keep a future one on-palette. The old escape hatch this bullet carried — red90 / red100 for an AA primary without leaving Streamlit's own palette — is moot now that the palette is the project's own
- **Two type keys, zero network fonts.** `headingFont = "serif"` sets the title — the page's only heading, and the only thing on it that can carry an identity — in Source Serif, bundled in the Streamlit wheel and served by the local server (the Roman woff2 is 429 KB, the largest asset the theme adds). `codeFont = "sans-serif"` sets the output `st.code` in Source Sans: the input `text_area` is `fontSizes.sm = 0.875rem` and the code block's inner `<code>` is `codeFontSize = 0.875rem`, so the two panels already matched at 14px and this one key makes translated prose read in the same face and size as the prose it came from — the panel is `st.code` only because that element can be replaced mid-stream and copied; its monospace was a side effect. `codeFontSize` is **deliberately unset**: anything larger than the default makes the output bigger than the input. Line heights and padding still differ (12px at 1.4 in the input, 16px at 1.6 in the code block — the first lines sit ~3px apart) and no theme key reaches either; that is geometry, not a theme bug. The bundle maps the generic names itself, so no `[[theme.fontFaces]]` block is needed, and `test_theme_fonts_are_bundled_not_fetched` fails on a `fontFaces` key in any table, a `://` in any `*Font` value (sidebar tables included), or a remote `base` — the caption's "nothing is sent to a server" makes a Google Fonts URL, which fires on every page load, a hard no. `baseFontSize` is untouched at Streamlit's 16px, so the historical `baseFontSize = 14` measurements flagged under Text tab are still historical
